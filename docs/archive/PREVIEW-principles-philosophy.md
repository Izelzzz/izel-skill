## worth-it-or-not（原 product-design-principles）

### 当前全文见

[`skills/worth-it-or-not/SKILL.md`](../../skills/worth-it-or-not/SKILL.md)

要点：

- 前置：先获取并理解项目已有事实，再做四项准则判断。
- 对内：第一性原理 / 奥卡姆剃刀 / **业务价值** / ROI；默认不展示。
- 当前对外骨架：首轮是状态句 + `## 已掌握的事实` + 恰好一道 `## 🔮 灵魂拷问`。作答后是状态句 + `## 已掌握的事实` + 自然语言消化；需要时再追问一个关键问题。

### 对外输出会变成什么样（运势推送例）

**Input：** 「加每日运势推送，竞品都有，能拉日活。」（暂无可及仓库上下文）

#### 旧版（长纪要，用户不关心）

```markdown
# 原则审查：每日运势推送

## 总体结论
因缺口中止

## 各项结论
### 第一性原理
- 判定：未通过
- 依据：……（大段）
### 奥卡姆剃刀 / 业务建模 / ROI
- ……（大段）
```

#### iteration-3 快照（结论 + 已掌握的事实 + 需要用户补充，最多 3 题）

```markdown
# 每日运势推送

## 结论
先补齐这几件事再谈

## 已掌握的事实
- 暂无项目上下文（未提供仓库/文档/已上线能力说明）；当前只能基于口述做假设性审查，结论效力受限。

## 需要用户补充（最多 3 题；答完后再决定是否续问）
1. 用户实际遇到的问题更接近哪一类？
   - A. 缺少每日运势内容本身
   - B. 打开 App 的理由不够（推荐：与「拉日活」叙事更一致，可先验证是否真缺打开理由，再决定要不要推送）
   - C. 尚不清楚，需要先访谈
2. 「竞品都有」之外，有没有访谈或行为证据说明用户因缺少每日运势而受损？若没有，本轮能否先补最小证据？
3. 上线后用什么指标算成功？请给出通过/失败门槛（打开率、次日留存增量 vs 对照、退订率、投诉率）。
```

## product-design-philosophy

### 新版全文见

[`skills/product-design-philosophy/SKILL.md`](../../skills/product-design-philosophy/SKILL.md)

交叉引用：方向未定时先做 `worth-it-or-not`（值不值得做）审查，再进入本 skill。

### 对外输出会变成什么样（支付「从未失败」例）

**Input：** 「支付页加一行『100% 安全到账，从未失败』，转化会更好。」

#### 旧版（方法表 + 各项判定长文）

```markdown
# 哲学审查：支付结果页「100% 安全到账，从未失败」文案
## 场景说明 / 方法选用 / 各项判定
……（大段）
## 总体结论
需修改
```

#### 新版（结论 + 可执行修改）

```markdown
# 支付结果页「100% 安全到账，从未失败」

## 结论
建议先改这些

## 建议修改
1. 把「100% 安全到账，从未失败」改成「支付已提交。到账结果以银行/支付渠道回执为准；工作日通常 2 小时内完成，失败将原路退回并短信/站内通知。」（去掉不可核验的绝对词，异常时可核对）
2. 若要强调安全：改写为可核对措施，例如「资金由持牌支付机构清算」「订单详情可查看流水号」，不要用「100%」「从未」
3. 结果页补「查看进度」与客服入口，让失败路径可控

## 还想确认
1. 当前真实到账时效与失败率大概是多少？（有数据可以把「通常 2 小时」收成更准的数字）
```
