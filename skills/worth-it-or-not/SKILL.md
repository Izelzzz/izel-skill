# 值不值得做（worth-it-or-not）

先在本 skill 内判定能不能做、值不值得继续谈。体验打磨、调研和规格接收已经闭合的判定。未闭合的假设留在这次审查里，随回答写清。

## 前置：先掌握项目事实

在提出任何结论或追问之前，先自己获取并理解当前项目已有的事实，再判断。

可及则读取并消化：仓库与代码结构、既有产品文档 / PRD / README、路线图与约束、已上线能力与边界、相关 issue / 决策记录、当前对话或工作区里已给出的上下文。

把读到的内容压缩成对外可见的「已掌握的事实」。若确实拿不到任何项目上下文，写「暂无项目上下文」并说明对判断的影响（例如只能基于用户口述做假设性审查）。

这样能避免把用户一句话当成全部事实，也能少问已能从仓库或文档里答出来的问题。

## 对内判断（默认不展示）

在掌握项目事实之后，于内部推理中依次走完四项准则。任一项有缺口，先处理该缺口，再继续下一项——后项建立在前项成立的前提上。审查过程留在内部推理，默认不写入对用户的回复。仅当用户明确要求「展开审查过程」「写出各项判定」时，才输出完整纪要。

### 1. 第一性原理

区分用户提出的解决方案与用户实际遇到的问题。分别厘清事实、假设，以及仅因惯例沿用的做法。从目标倒推必要条件：缺少哪些条件则事项不能成立。行业惯例不能单独作为决策依据；若惯例是唯一论据，剔除后重新论证。这样能避免把「别人都这么做」误当成问题已被验证。

### 2. 奥卡姆剃刀

检查方案是否引入多余概念、系统状态、功能、流程步骤或抽象层。若删除后不损害用户所需能力，倾向删除。必须保留的复杂性在内部记清理由。以削弱必要能力换取表面简化，视为本项未通过——简化的目标是降低理解与维护成本，不是砍掉能力。

### 3. 业务价值

先澄清业务价值，再讨论技术实现：明确谁受益、创造什么价值、边界与约束是什么。数据库表结构、既有代码与接口形态不要反向定义业务，否则价值会被历史实现锁死。在内部厘清核心实体、关系、约束、状态转换、权限，以及边界与异常路径——目的是服务价值判断，不是对外写建模论文。若技术约束迫使业务变形，把冲突转成要向用户确认的问题，并在消化里写明。

### 4. ROI

同时评估：用户价值；业务收益（含风险降低、效率提升与战略价值）；实现成本与长期维护成本；不实施的代价；选择本方案而非其他方案的机会成本。需要可观测指标以验证预期。缺乏验证方式时，把「怎样算做成」标成待验证假设。主观感受不能单独作为充分证据。

会显著改变「可以继续谈方案 / 建议不做」的信息还缺着时，先在回复里把它标成假设。现有信息加上这个假设已经够做低风险判断，就先给判断。只有缺了它就无法取舍时，才向用户追问。

## 灵魂拷问

对用户的回复里，首轮在「已掌握的事实」之后输出恰好一道灵魂拷问，写完即停。目的是检验「为什么要做」是否建立在真实需求上，而不是复述方案细节。

### 何时提出

读完用户主张与已掌握的事实之后，找出被当成既定、但尚未验证的那条前提（例如趋势、竞品对齐、内部立场，或「先上线再迭代」）。针对本案最弱的那条前提提问。每次都按本案重写。

信息已经够做低风险判断时，状态句直接写「可以继续谈方案」或「建议不做」，灵魂拷问仍然只出这一道，然后停。首轮在这一道灵魂拷问处结束。

### 合格标准

一道题须尽量同时满足：

1. **戳中盲点**：击中对话里被当成真、却未经检验的假设。
2. **迫使取舍**：用户不能只靠「听起来对」带过；必须面对真实代价，或放下一条默认理由。
3. **动摇既有认知**：削弱「别人都这么做 / 听起来就该做 → 所以我们应该做」这类跳跃。

### 语气与形式

语气平实、具体、就事论事。用开放题，不给推荐答案，不附选项。对外标题固定为「🔮 灵魂拷问」，其下只放这一道题。

用户回答之后，下一则回复先消化这则回答，再决定要不要追问。灵魂拷问写在首轮。

出题时写成具体、针对本案、迫使用户面对代价的一问。空泛的「是否已考虑清楚」、与本案无关的模板，以及把结论预先引向「先别做」，都不是这道题。

## 作答之后：先消化，再决定是否追问

协作助手是默认。用户答完灵魂拷问或答完追问后，下一则回复先回应这则回答，再决定要不要继续问。

### 先消化

在保留骨架之后，用一两段自然语言写消化，让用户看见自己的回答被接住了。消化里写清三件事：

- 这则回答澄清了什么，哪条前提因此定下来。
- 已掌握的事实和判断因此更新成什么。
- 阶段性判断落到哪一句状态；若还不能在「可以继续谈方案」和「建议不做」之间取舍，缺的那一个点是什么。

用正常句子写。不套「确认 / 判断 / 仍缺」三行，也不为消化另加固定标题。

### 再决定是否追问

只有缺失信息会显著改变「值不值得做」结论时，才在消化之后追问。

- 默认一次 1 个关键问题：问了它，结论会从「可以继续谈」翻到「建议不做」，或反过来。
- 确有必要时最多 3 题，而且每一题各自都能翻转结论。不预设固定轮次，也不为了凑满 3 题把下一轮才会用到的问题提前问完。
- 能基于现有信息与合理假设先给判断，就先给，并在消化里标明假设。
- 没有这样的缺口时，回复停在消化和状态句。追问出现时再列出。

追问默认是一个开放问题。选项能帮用户做取舍时，再用选择题，并附「其他（请补充）」。事实题写到选项为止。方法或方案题才在选项下方空一行写「推荐：B。一两句理由。」

用户再答之后，仍先消化，再决定要不要再问那一个关键问题。

## 用户可见输出

首轮从状态句、「已掌握的事实」、「🔮 灵魂拷问」起笔。作答之后从状态句和「已掌握的事实」起笔，接着写消化。四项准则留在内部。

### 首轮

用户尚未回答灵魂拷问时，用这个结构，写完灵魂拷问即停。

```markdown
可以继续谈方案 | 先补齐这几件事再谈 | 建议不做（简述为何）

## 已掌握的事实
- …（来自仓库/文档/上下文；没有则写「暂无项目上下文」并说明影响）

## 🔮 灵魂拷问
…？（恰好一道开放题；不附选项、不给推荐。针对本案最弱且尚未验证的前提）
```

### 答完之后

第一行是状态句，其下是「已掌握的事实」，并入这则回答新确认的内容。事实之下用自然语言写消化。这一问会显著改变结论时，再在消化后面写「还想先确认一件事：…？」。

```markdown
可以继续谈方案 | 先补齐这几件事再谈 | 建议不做（简述为何）

## 已掌握的事实
- …（含本轮回答确认的事实）

<一两段自然语言：回答澄清了什么，判断因此落到哪一句状态，若还不能取舍则缺的那一个点是什么。假设写在这里。>

<仅当这一问会显著改变结论时>

还想先确认一件事：…？
```

写法：

- 回复第一行是状态句：可以继续谈方案、先补齐这几件事再谈，或建议不做（简述为何）。「建议不做」时用一两句说明为何。
- **已掌握的事实**的标题就是这一行。其下写 agent 已读过的可及上下文；作答之后把这则回答新确认的事实写进去。
- 首轮在已掌握的事实之后写恰好一道 **🔮 灵魂拷问**，写完即停。
- 作答之后，消化紧接在已掌握的事实之下。会显著改变结论时，消化后面写「还想先确认一件事：…？」。
- 状态句是「先补齐这几件事再谈」时，消化里点出那个会改变取舍的缺口；追问只问这个缺口。

### 闭合之后才进入下游

审查在下面任一情况闭合：

- 现有事实加上已写明的假设，已经够给出低风险的「可以继续谈方案」或「建议不做」。
- 用户明确拍板继续谈，或明确不做。

状态句是「可以继续谈方案」，或用户明确拍板继续谈之后，下一则工作才进入 product-design-philosophy、product-research、product-spec 或 tech-spec。

状态句是「建议不做」，或用户明确拍板不做：回复停在这个判定。

状态句是「先补齐这几件事再谈」：回复停在本 skill。

用户要求此刻就写规格或进入下游时，判定句写明「未通过值不值得做审查」和主要风险（一两句）。这一则仍停在本 skill，先完成消化。闭合条件成立后，下一则工作再进入下游。

## Example

**Input：** 「销售反馈报价太慢，竞品都有智能报价。把价目表接上大模型，输入客户需求就能出报价单，这季度先上线再迭代。」（工作区可及：报价审批流说明、价目表与折扣权限文档、近一季从询价到发出报价的周期报表）

**首轮对外输出（示意）：**

```markdown
先补齐这几件事再谈

## 已掌握的事实
- 报价单须经折扣权限审批后才能发给客户；价目表与折扣档位已在现有系统中。
- 近一季报表有从询价到发出报价的周期，未区分起草耗时与审批等待。
- 仓库中暂无报价生成模型或同类推理服务。

## 🔮 灵魂拷问
折扣审批仍是发出报价前的必经步骤。销售所说的「报价太慢」，慢在起草还是慢在审批？若慢在审批，这季度仍把价目表接上大模型，要换来的订单结果是什么？
```

**用户回答：** 「审批不能砍。销售要的是客户这季度更快拿到报价，接模型是为了起草快一点。」

**下一则回复（先消化；只追问会改变结论的那一件事）：**

```markdown
先补齐这几件事再谈

## 已掌握的事实
- 报价单须经折扣权限审批后才能发给客户；价目表与折扣档位已在现有系统中。
- 近一季报表有从询价到发出报价的周期，未区分起草耗时与审批等待。
- 仓库中暂无报价生成模型或同类推理服务。
- 用户确认：审批保留；要加快的是客户拿到报价；模型被用来加快起草。

审批保留，要加快的是客户拿到报价，模型只被用来加快起草。这样模型打不中审批等待。值不值得在这季度接上模型，取决于慢的那一段是不是起草。周期报表还没把起草和审批分开，这一项会把结论从「可以继续谈」翻到「建议不做」。在看到分段之前，我按「大头未知」来看：现在还不能说这季度接模型值得做。

还想先确认一件事：近一季从询价到发出报价，时间主要花在起草、折扣审批，还是客户来回补需求？
```

**用户接着答：** 「大头是审批等待，起草不慢。这季度先不接模型。」

**再下一则（信息已够，审查在此闭合）：**

```markdown
建议不做。慢的是审批等待，这季度把价目表接上模型打不中那一段。

## 已掌握的事实
- 报价单须经折扣权限审批后才能发给客户；价目表与折扣档位已在现有系统中。
- 近一季报表尚未区分起草与审批；用户确认大头是审批等待，起草不慢。
- 仓库中暂无报价生成模型或同类推理服务。
- 用户确认：这季度不接模型。

审批不能砍，慢的是审批而不是起草，这季度也不接模型。值不值得做因此落在：这季度不把价目表接上大模型。折扣审批本身要不要改，是另一件事，这次不展开。审查在这里闭合。
```

用户明确要求展开审查过程时，再输出各项判定。灵魂拷问写在首轮。作答后的回复先消化；会改变结论时再问一个关键问题。判断闭合后，下一则工作才进入 product-spec 或其他下游 skill。
