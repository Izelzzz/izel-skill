# 值不值得做（worth-it-or-not）

先在本 skill 内判定能不能做、值不值得继续谈，并写出闭合状态，再进入体验打磨或规格编写。未闭合的假设留在本审查里，随回答消化写清。PRD 与实现接收已经闭合的判定。一次短对话澄清的成本，通常低于返工。

## 前置：先掌握项目事实

在提出任何结论或追问之前，**必须先自己获取并理解当前项目已有的事实**，再判断。不要一上来只针对用户的问题提问。

可及则读取并消化：仓库与代码结构、既有产品文档 / PRD / README、路线图与约束、已上线能力与边界、相关 issue / 决策记录、当前对话或工作区里已给出的上下文。

把读到的内容压缩成对外可见的「已掌握的项目事实」（极短）。若确实拿不到任何项目上下文，写「暂无项目上下文」并说明对判断的影响（例如只能基于用户口述做假设性审查）。

这样能避免把用户一句话当成全部事实，也能少问已能从仓库/文档里答出来的问题。

## 对内判断（默认不展示）

在掌握项目事实之后，于内部推理中依次走完四项准则；任一项有缺口则先处理该缺口，再继续下一项——后项建立在前项成立的前提上。审查过程留在内部推理，**默认不写入对用户的回复**。仅当用户明确要求「展开审查过程」「写出各项判定」时，才输出完整纪要。

### 1. 第一性原理

区分用户提出的解决方案与用户实际遇到的问题。分别厘清事实、假设，以及仅因惯例沿用的做法。从目标倒推必要条件：缺少哪些条件则事项不能成立。行业惯例不能单独作为决策依据；若惯例是唯一论据，剔除后重新论证。这样能避免把「别人都这么做」误当成问题已被验证。

### 2. 奥卡姆剃刀

检查方案是否引入多余概念、系统状态、功能、流程步骤或抽象层。若删除后不损害用户所需能力，倾向删除。必须保留的复杂性在内部记清理由。以削弱必要能力换取表面简化，视为本项未通过——简化的目标是降低理解与维护成本，不是砍掉能力。

### 3. 业务价值

先澄清业务价值，再讨论技术实现：明确谁受益、创造什么价值、边界与约束是什么。数据库表结构、既有代码与接口形态不要反向定义业务，否则价值会被历史实现锁死。在内部厘清核心实体、关系、约束、状态转换、权限，以及边界与异常路径——目的是服务价值判断，不是对外写建模论文。若技术约束迫使业务变形，把冲突转成要向用户确认的问题，不要隐瞒。

### 4. ROI

同时评估：用户价值；业务收益（含风险降低、效率提升与战略价值）；实现成本与长期维护成本；不实施的代价；选择本方案而非其他方案的机会成本。需要可观测指标以验证预期。缺乏验证方式则本项未闭合——主观感受不能作为充分证据。

关键信息不足时，向提出方追问。必须推进时，把臆测标为假设，放进回答消化之后、为闭合判断而提出的追问里，并标明这是假设。已确认事实只写用户回答或项目材料里已经定下的内容。

## 灵魂拷问

对用户的回复里，首轮在「已掌握的项目事实」之后输出恰好一道灵魂拷问，写完即停。目的是检验「为什么要做」是否建立在真实需求上，而不是复述方案细节。

### 何时提出

读完用户主张与已掌握的项目事实之后，找出被当成既定、但尚未验证的那条前提（例如趋势、竞品对齐、内部立场，或「先上线再迭代」）。针对**本案**最弱的那条前提提问。不要每次都把趋势、意图、自欺拼成同一道题；不要使用与本案无关的套话。

### 合格标准

一道题须尽量同时满足：

1. **戳中盲点**：击中对话里被当成真、却未经检验的假设。
2. **迫使取舍**：用户不能只靠「听起来对」带过；必须面对真实代价，或放下一条默认理由。
3. **动摇既有认知**：削弱「别人都这么做 / 听起来就该做 → 所以我们应该做」这类跳跃。

### 语气与形式

语气平实、具体、就事论事。不嘲讽，不施压，不把结论引向「保守起见先别做」。用开放题；**不给推荐答案**，不附选项。对外标题固定为「🔮 灵魂拷问」，其下只放这一道题。

用户回答灵魂拷问之后，下一则回复先写「回答消化」，再按消化里的「仍缺」决定追问。回答消化写三句：该回答确认的前提；值不值得做判断因此落到哪一句状态；尚未闭合的条件。追问只补这些仍缺条件，一道题对应一条条件，本轮最多 3 题，灵魂拷问另计。仍缺为「无」时，本则回复以闭合判定收束。追问用一句短引导起头，沿用正文骨架。灵魂拷问保持已提出的那一道。

### 不合格出题

不要使用下列问法：

- 空泛质疑，例如「是否已考虑清楚？」「是否存在跟风嫌疑？」——既容易被一句带过，语气也像指责。
- 与本案无关的模板句；或把多件互不相关的质疑塞进同一道题。
- 把结论引向保守，或替用户预先否决方案。

## 用户可见输出

首轮与作答之后的回复，都从同一骨架起笔：标题、状态句、已掌握的项目事实、🔮 灵魂拷问。作答之后的回复在灵魂拷问之下先写回答消化；仍缺闭合条件时，消化之后才是追问。四项准则留在内部推理。用户明确要求「展开审查过程」「写出各项判定」时，再输出完整纪要。

### 首轮

用户尚未回答灵魂拷问时，ALWAYS use this exact structure. 写完灵魂拷问即停。首轮骨架只有标题、状态句、已掌握的项目事实、🔮 灵魂拷问。后续追问留到用户作答并写完回答消化之后。

```markdown
# <需求一句话>
可以继续谈方案 | 先补齐这几件事再谈 | 建议不做（简述为何）

## 已掌握的项目事实（极短）
- …（来自仓库/文档/上下文；没有则写「暂无项目上下文」并说明影响）

## 🔮 灵魂拷问
…？（恰好一道开放题；不附选项、不给推荐。针对本案最弱且尚未验证的前提）
```

### 答完灵魂拷问或追问之后

每一则用户回答（灵魂拷问或追问）的下一则回复，都先写回答消化，再决定追问或闭合。保留标题、状态句、已掌握的项目事实，以及已经提出的那一道灵魂拷问。项目事实并入这则回答新确认的内容。灵魂拷问保持已提出的那一题。

在灵魂拷问之下写 `## 回答消化`，三句，写在给用户的回复里：

- 确认：这则回答把哪条前提定下来
- 判断：状态句因此是「可以继续谈方案」「先补齐这几件事再谈」或「建议不做」（简述为何）
- 仍缺：还缺哪几条闭合条件；已经能在「可以继续谈方案」与「建议不做」之间取舍时写「无」

仍缺列出条件时，状态句与判断都写「先补齐这几件事再谈」，消化写完后再追问。引导句短而正式，例如「还想确认这几件事：」。本轮题数等于仍缺的条数，最多 3 题。每道题只闭合一条仍缺条件。仍缺多于 3 条时，本轮问最影响「可以继续谈方案 / 建议不做」取舍的 3 条；用户作答后先消化，再问其余。仍缺为「无」时，状态句与判断同为「可以继续谈方案」或「建议不做」，回复停在回答消化。

```markdown
# <需求一句话>
可以继续谈方案 | 先补齐这几件事再谈 | 建议不做（简述为何）

## 已掌握的项目事实（极短）
- …（含本轮回答确认的事实）

## 🔮 灵魂拷问
…？（保留已提出的那一题）

## 回答消化
- 确认：…
- 判断：先补齐这几件事再谈
- 仍缺：…；…（已能取舍时写「无」，回答消化就是本则回复的结尾）

还想确认这几件事：

1. …？（询问事实；对应一条仍缺条件）
   - A. …
   - B. …
   - C. 其他（请补充）

---

2. …？（询问方法/方案；该取舍仍决定值不值得做时才问）
   - A. …
   - B. …
   - C. …
   - D. 其他（请补充）

   推荐：B。一两句理由…
```

### 闭合后的交接

「回答消化」的仍缺为「无」，且状态句是「可以继续谈方案」时，本审查闭合。下一则工作才进入 product-design-philosophy、product-research、product-spec 或 tech-spec。

仍缺为「无」，且状态句是「建议不做」时，审查在本 skill 内闭合，回复停在该判定。

状态句是「先补齐这几件事再谈」时，回复停在本 skill。用户再答之后，下一则仍先写回答消化，再按新的仍缺条件追问，每轮最多 3 题。

写法要求：

- 标题下一行用一句说清状态：可以继续谈方案、先补齐这几件事再谈，或建议不做（简述为何）。「建议不做」时用一两句说明为何，不要展开四项打分。不要另起「结论」标题。
- **已掌握的项目事实**必写：展示 agent 已读过的可及上下文（或明确暂无）。不要把审查过程写进这里。
- **🔮 灵魂拷问**必写，且只写一道开放题，放在「已掌握的项目事实」之后。标题固定为「🔮 灵魂拷问」。开放题只写题干。出题按上一节执行。首轮只出灵魂拷问，写完即停。用户作答后的下一则回复仍保留已提出的那一题，并先写回答消化。
- **回答消化**写在灵魂拷问之下、任何追问之上。三句为确认、判断、仍缺。这三句是对用户回答的回应，各一句，四项准则的展开留在内部。
- **追问**：放在回答消化之后，只问仍缺里列出的闭合条件。一句引导起头，例如「还想确认这几件事：」。一行一个问题。能列出具体选项时用选择题，并附带开放项（其他 / 开放填写），让用户能自己填写。事实题写到开放项为止。方法/方案题在全部选项下方空一行写推荐，格式为「推荐：B。一两句理由。」列不出具体选项时用问答题。本轮题数等于仍缺条数，最多 3 题，灵魂拷问另计。题与题之间用 `---` 分隔。用户再答之后，先写回答消化，再决定下一轮追问或闭合。有推荐时，推荐前空一行，用下面这种格式：

```
2. …？
   - A. …
   - B. …
   - C. …
   - D. 其他（请补充）

   推荐：B。一两句理由…
```
- **交接**：仍缺为「无」且状态句为「可以继续谈方案」之后，才写 product-spec，或进入 product-design-philosophy、product-research、tech-spec。仍缺为「无」且状态句为「建议不做」时，回复停在本判定。状态句为「先补齐这几件事再谈」时，回复停在本 skill。对外状态只用「可以继续谈方案」「先补齐这几件事再谈」「建议不做」这三句。
- 提出方要求进入 product-spec 或其他下游 skill 时，判定句写明「未通过值不值得做审查」与主要风险（一两句）。回复仍停在本 skill，下一则继续回答消化。仍缺为「无」且状态句为「建议不做」时，回复停在该判定。仍缺为「无」且状态句为「可以继续谈方案」之后，才进入下游 skill。

## Example

**Input：** 「销售反馈报价太慢，竞品都有智能报价。把价目表接上大模型，输入客户需求就能出报价单，这季度先上线再迭代。」（工作区可及：报价审批流说明、价目表与折扣权限文档、近一季从询价到发出报价的周期报表）

**首轮对外输出（示意）：**

```markdown
# 智能报价
先补齐这几件事再谈

## 已掌握的项目事实
- 报价单须经折扣权限审批后才能发给客户；价目表与折扣档位已在现有系统中。
- 近一季报表有从询价到发出报价的周期，未区分起草耗时与审批等待。
- 仓库中暂无报价生成模型或同类推理服务。

## 🔮 灵魂拷问
折扣审批仍是发出报价前的必经步骤。销售所说的「报价太慢」，慢在起草还是慢在审批？若慢在审批，这季度仍把价目表接上大模型，要换来的订单结果是什么？
```

**用户回答：** 「审批不能砍。销售要的是客户这季度更快拿到报价，接模型是为了起草快一点。」

**下一则回复（先消化，再只追问仍缺的闭合条件）：**

```markdown
# 智能报价
先补齐这几件事再谈

## 已掌握的项目事实
- 报价单须经折扣权限审批后才能发给客户；价目表与折扣档位已在现有系统中。
- 近一季报表有从询价到发出报价的周期，未区分起草耗时与审批等待。
- 仓库中暂无报价生成模型或同类推理服务。
- 用户确认：审批保留；要加快的是客户拿到报价；模型被用来加快起草。

## 🔮 灵魂拷问
折扣审批仍是发出报价前的必经步骤。销售所说的「报价太慢」，慢在起草还是慢在审批？若慢在审批，这季度仍把价目表接上大模型，要换来的订单结果是什么？

## 回答消化
- 确认：折扣审批保留；要加快的是客户拿到报价；模型被用来加快起草。
- 判断：先补齐这几件事再谈。审批保留时，模型只作用在起草；值不值得做取决于慢的那一段是不是起草。
- 仍缺：发出周期里占大头的是哪一段；周期拆开之前，这季度的判定落在先测量，还是直接全量接入。

还想确认这几件事：

1. 近一季发出周期里，哪一段占大头？
   - A. 起草报价
   - B. 折扣审批等待
   - C. 客户补充需求来回
   - D. 其他（请补充）

---

2. 周期还没拆开之前，这季度的值不值得做判定落在哪一件事上？
   - A. 先用两周把起草和审批耗时拆开，再决定模型是否值得接
   - B. 这季度就全量把价目表接上模型，订单结果上线后再看
   - C. 这季度不做报价链路改动
   - D. 其他（请补充）

   推荐：A。报表还没分开起草与审批，先拆开才能判断模型是否打在真正变慢的那一段上。
```

这两题分别对应仍缺的两条条件，所以本轮停在两题。用户明确要求展开审查过程时，再输出各项判定。灵魂拷问恰好一道。用户作答后的回复先写回答消化，再按仍缺条件提出事实题或方法题，本轮最多 3 题。仍缺为「无」且状态句为「可以继续谈方案」之后，下一则工作才进入 product-spec 或其他下游 skill。状态句仍是「先补齐这几件事再谈」时，回复停在本 skill。
