# 值不值得做（worth-it-or-not）

先判定「能不能做 / 值不值得继续谈」，再进入体验打磨或规格编写。跳过本审查会把未澄清的假设带进 PRD 与实现，返工成本通常高于一次短对话澄清。

## 前置：先掌握项目事实

在提出任何结论或追问之前，**必须先自己获取并理解当前项目已有的事实**，再判断。不要一上来只针对用户的问题提问。

可及则读取并消化：仓库与代码结构、既有产品文档 / PRD / README、路线图与约束、已上线能力与边界、相关 issue / 决策记录、当前对话或工作区里已给出的上下文。

把读到的内容压缩成对外可见的「已掌握的项目事实」（极短）。若确实拿不到任何项目上下文，写「暂无项目上下文」并说明对判断的影响（例如只能基于用户口述做假设性审查）。

这样能避免把用户一句话当成全部事实，也能少问已能从仓库/文档里答出来的问题。

## 对内判断（默认不展示）

在掌握项目事实之后，于内部推理中依次走完四项准则；任一项有缺口则先处理该缺口，再继续下一项——后项建立在前项成立的前提上。审查过程留在内部推理，**默认不写入对用户的回复**。仅当用户明确要求「展开审查过程」「写出各项判定」时，才输出完整纪要。

### 1. 第一性原理

区分用户提出的解决方案与用户实际遇到的问题。分别厘清事实、假设，以及仅因惯例沿用的做法。从目标倒推必要条件：缺少哪些条件则事项不能成立。行业惯例不能单独作为决策依据；若惯例是唯一论据，剔除后重新论证。这样能避免把「别人都这么做」误当成问题已被验证。

### 2. 奥卡姆剃刀

检查方案是否引入多余概念、系统状态、功能、流程步骤或抽象层。若删除后不损害用户所需能力，倾向删除。必须保留的复杂性在内部记清理由。以削弱必要能力换取表面简化，视为本项未通过——简化的目标是降低理解与维护成本，不是砍掉能力。

### 3. 业务价值

先澄清业务价值，再讨论技术实现：明确谁受益、创造什么价值、边界与约束是什么。数据库表结构、既有代码与接口形态不要反向定义业务，否则价值会被历史实现锁死。在内部厘清核心实体、关系、约束、状态转换、权限，以及边界与异常路径——目的是服务价值判断，不是对外写建模论文。若技术约束迫使业务变形，把冲突转成需要用户补充的问题，不要隐瞒。

### 4. ROI

同时评估：用户价值；业务收益（含风险降低、效率提升与战略价值）；实现成本与长期维护成本；不实施的代价；选择本方案而非其他方案的机会成本。需要可观测指标以验证预期。缺乏验证方式则本项未闭合——主观感受不能作为充分证据。

关键信息不足时，向提出方追问，不要臆测；必须推进时，把臆测标为假设并写进「需要用户补充」。

## 用户可见输出

ALWAYS use this exact structure. 不要输出「各项判定 / 依据 / 方法表」式长纪要。

```markdown
# <需求一句话>

## 结论
可以继续谈方案 | 先补齐这几件事再谈 | 建议不做（简述为何）

## 已掌握的项目事实（极短）
- …（来自仓库/文档/上下文；没有则写「暂无项目上下文」并说明影响）

## 需要用户补充（最多 3 题；答完后再决定是否续问）
1. …？（问答题）
2. …？
   - A. …
   - B. …（推荐：<一两句理由>）
   - C. …
```

写法要求：

- **结论**用一句说清状态；「建议不做」时用一两句说明为何，不要展开四项打分。
- **已掌握的项目事实**必写：展示 agent 已读过的可及上下文（或明确暂无）。不要把审查过程写进这里。
- **需要用户补充**：一行一个问题；类型为选择题或问答题；选择题必须带**推荐答案**，并在推荐选项旁注明**推荐理由**（一两句即可，说明为何倾向该项）；不要只标「推荐」而无解释；**一次最多问 3 个问题**。把内部发现的、且无法从项目事实推出的缺口翻译成追问，而不是复述审查过程。得到用户回复后，再判断是否还要继续追问下一轮（仍 ≤3）。
- 缺口未补前：不要写 PRD、不要排期上线、不要宣称可上线。可以说方向值得继续聊，但必须先把追问闭环。
- 提出方坚持跳过审查时，可继续协助，但在结论中注明「未通过值不值得做审查」并点出主要风险（一两句即可）。

## Example

**Input：** 「我们要给后台加一个 AI 自动分类工单的功能，竞品都有，尽快上。」（工作区可及：售后后台 README、工单分类路由代码、近 30 天处理量看板截图）

**对外应输出的形态（示意）：**

```markdown
# AI 自动分类工单

## 结论
先补齐这几件事再谈

## 已掌握的项目事实
- 售后后台已有人工分类与路由；近 30 日日均工单约可从看板读到量级，但未见准确率/耗时基线文档。
- 仓库里暂无模型推理服务或训练流水线；路由逻辑目前是规则 + 人工。

## 需要用户补充（最多 3 题；答完后再决定是否续问）
1. 现在工单分类的真实痛点主要是哪一类？
   - A. 不准（常分错类）（推荐：可量化，且与「上模型」直接相关，便于验证业务价值）
   - B. 太慢（积压）
   - C. 人手不够
2. 上线后用什么指标算成功？请给出通过/失败门槛（例如准确率、人均处理时长、误分类回滚率）。
3. 若先不上模型，用「规则扩写 + 人工抽检」做两周对照，能否覆盖主要场景？若不能，卡在哪？
```

不要对外展开「第一性原理未通过 / 依据三段」之类纪要，除非用户明确要求展开审查过程。一次不要超过 3 题；用户答完本轮后，再决定是否续问。
