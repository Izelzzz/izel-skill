# 推送安全、危险操作、冲突与失败

准备推送、force-push、`reset`、`clean`、改写历史、丢弃改动，或命令失败、出现冲突时，阅读本文件。决策顺序在 `SKILL.md`。本文件不放宽平台的安全限制。直推授权只覆盖对点名分支的普通推送，不包含本节的高风险操作。

## 推送

推送前确认这六件事：

1. 当前分支全名。
2. 远程名，通常先用 `git remote -v` 核对，不要把 origin 想成另一个仓库。
3. 目的地分支。没写目的地时，Git 可能更新当前跟踪分支，先看清跟踪关系。
4. 跟踪分支是什么，本地比远程超前还是分叉。
5. 将要送出的提交：`git log --oneline <remote>/<branch>..HEAD`，以及对应 diff。
6. 这次推送会不会覆盖远端，或触发部署、发布钩子。

只推送预定分支。不要在同一条命令里夹带其他 ref。

下面的做法禁止使用：

- 对共享分支 force-push。共享包括发布分支、仓库默认分支、其他人正在使用的分支，以及 Izelzzz/izel-skill 的 `feature/global`。
- 用 `--force` 让一次被拒绝的推送「通过」。
- 绕过分支保护、权限或钩子。
- 在未查看两边差异时，把分叉的历史推上去。

本地与远程分叉时：用 `git fetch` 后查看远程新增了什么，再按仓库政策决定。改写共享历史之前，必须同时满足「确有必要、政策允许、用户明确授权」。这三项缺一，就停下来说明分叉，不要推送。

`--force-with-lease` 会改写已发布历史。它不是普通推送的安全替代品。必要、政策允许、用户对本分支的 force-push 明确授权，这三项同时成立时才使用。授权只覆盖被点名的分支。用户说「推不上去你处理一下」并没有授权 force-push。

普通 `git push` 被拒绝时：停止，报告拒绝原因和当前分支。不要改试 `--force`。不要反复重试同一条被拒绝的命令。

## 高风险操作

这些操作属于高风险：

- `git reset --hard`
- `git clean -fd`，以及任何会删除未跟踪文件的 `git clean`
- force-push，包括 `--force` 与 `--force-with-lease`
- 改写共享历史（已推送提交上的 amend、rebase 后强推、丢掉已发布提交的 reset）
- 删除仍含有未合并且有价值工作的分支
- 丢弃用户改动
- 冲突时用一侧覆盖另一侧
- 用 `--no-verify` 或关闭检查来绕过钩子、权限和校验

执行前按顺序做完：

1. 向用户说明会影响哪些路径、提交或远程 ref。
2. 检查未提交的工作和尚未合并的有价值提交。
3. 确认没有更小、可回退的办法。
4. 取得对本轮、本操作、本目标的授权。上一轮的同意不算本轮的同意。工具的默认权限不算用户授权。
5. 能用可回退的做法就不用不可回退的做法。例如用新提交撤销，而不是改写已发布历史。

禁止：

- 为了让工作区变干净、让切换分支顺利、或让提交更好看，藏起、丢掉或覆盖用户改动。
- 自动加上 `--ours` 或 `--theirs`。
- 把密钥、凭据、令牌或环境文件提交进仓库。
- 没有命令输出或对象链接就报告成功。
- 绕过访问控制、分支保护或仓库要求的检查。

对会不会丢失数据没有把握时，停止并询问。不要先做再解释。

视为用户改动、并且在没有点名授权时必须保留的内容：

- 任务开始时工作区或暂存区里已经存在、且不是本次任务写出的修改。
- 用户在任务进行中写入的文件。
- 无法判断作者的未提交修改。

这些路径不要 `git add`，不要用工具覆盖，不要 `git restore` 或 `git checkout --` 还原。本次任务自己写出的文件可以继续编辑和提交。与用户改动落在同一文件、又分不开 hunk 时，按下面的冲突处理。

Agent 刚刚写出、且尚未提交、作者可以确定的文件，可以只撤那些路径。无法确定作者时，按用户改动处理。

## 命令失败

失败时按这个顺序处理，不要跳到重试：

1. 读完整错误输出，包括远程拒绝的那一句。
2. 检查状态：`git status --short --branch`，必要时看 `git diff` 和最近的 `git log`。
3. 把原因归类：权限或保护规则、网络、分叉、冲突、钩子失败、本地未提交改动挡住了命令、命令本身用错。
4. 选择破坏最小的恢复。能用只读命令确认的，先只读确认。
5. 归类已经说明原来的命令不能成功时，不要原样重试。

钩子或测试失败时，修提交内容或说明失败原因。不要用 `--no-verify` 把失败藏掉。

## 冲突

合并、rebase、cherry-pick、pull，或即将写入的路径上已有用户改动，都按冲突处理。

1. 同时查看两侧：用户现有内容，以及本次准备写入的内容。列出冲突路径。
2. 与本次任务无关的用户改动留在原地，不暂存，不还原。
3. 只有意图清楚时才编辑冲突标记并完成操作。意图清楚，指用户已经说明每一处保留哪一侧，或任务目标与两侧差异能够无歧义对应。为了赶进度而猜的取舍，不算清楚。
4. 解决之后运行仓库要求的测试，并检查最终 diff，确认没有把无关改动带进来，也没有留下冲突标记。
5. 意图不清楚时停止并询问。在回答之前不要提交、不要推送、不要开 PR。

不要把失败的合并或推送报告成已经完成。

推送时发现远程比本地超前：停止。`git fetch` 之后说明远程新增了什么。不要在 pull 时强行覆盖本地，不要 force-push。
