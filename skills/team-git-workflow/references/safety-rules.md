# 危险操作、用户改动保护与冲突处理

准备 force-push、`reset`、`clean`、覆盖工作区文件，或发现与用户改动冲突时，阅读本文件。本文件是 `team-git-workflow` 的安全规则，优先级高于直推授权与开 PR。入口在 `skills/team-git-workflow/SKILL.md`。

直推授权只覆盖对点名分支的普通 `git push`。它不包含 force-push，不包含丢弃未提交改动，也不包含在冲突时替用户选择一侧。

## 明确同意

危险操作需要用户在本轮对话里同时点名操作和目标。

构成同意的例子：

- 「可以对 `feature/global` force-push。」
- 「可以 `reset --hard`，丢掉我本地这三处修改。」
- 「这几个未跟踪文件可以用 `clean -fd` 删掉。」并点名了文件或目录。

不构成同意的例子：

- 「直接推到 `feature/global`，不要开 PR。」这只同意普通 push。
- 「你看着办。」
- 运行环境或工具说明里的默认权限。
- 上一轮任务里的同意。本轮没有重申，则本轮没有同意。

同意只覆盖被点名的操作和被点名的分支或路径。不要把对一个分支的同意用到另一个分支上。

## force-push

共享分支与指定工作分支在没有明确同意时，禁止 force-push。本仓库的 `feature/global`、`main`、`master` 都在此列。用户称为共享的其他分支同样在此列。

即使用户同意 force-push，目标若是 `main` 或 `master`，用户还须点名 `main` 或 `master`。只说「主干」时，询问是哪一条，得到点名再执行。

用户同意之后，只对该分支使用 `git push --force-with-lease`。`--force-with-lease` 仍然改写已发布历史，同样需要上述同意。不要对未被点名的分支加 `--force`。

普通 `git push` 被拒绝（远程有新提交、非快进）时：停止，说明拒绝原因。不要改用 force-push，除非用户随后对本分支给出明确同意。

## 丢弃未提交改动

下列命令会丢掉工作区或暂存区里的内容。没有明确同意时，禁止执行：

- `git reset --hard`
- `git clean -fd` 以及会删除未跟踪文件的 `git clean` 选项
- `git checkout -- <路径>` 或 `git restore` 作用在用户改过的文件上
- 丢弃用户 stash 的 `git stash drop` 与 `git stash clear`

需要撤掉 Agent 自己刚刚写出、且尚未提交的文件时，可以只撤那些能确定是本次写出的路径。无法确定作者时，按用户改动处理：停止并询问。

## 用户改动

视为用户改动：

- 任务开始时工作区或暂存区里已经存在、且不是本次 Agent 写出的修改。
- 用户在 Agent 工作期间写入的文件。
- 无法判断作者的未提交修改。

这些路径不要纳入 `git add`，不要用工具覆盖，不要用 `restore` 或 `checkout --` 还原，除非用户点名了路径并同意覆盖或还原。

Agent 自己在本次任务中写出的文件，可以继续编辑、暂存和提交。与用户改动落在同一文件时，按下一节的冲突处理。

## 冲突处理

与用户本地改动冲突，或即将写入的路径上已有用户改动时：

1. 停止。不要继续 commit、push、开 PR。
2. 列出冲突路径。
3. 用几句话说明两侧分别是什么：用户现有内容，以及本次准备写入的内容。
4. 询问保留哪一侧，或是否由用户自行合并。
5. 在用户回答之前，不要写这些路径，不要使用 `--ours` 或 `--theirs`，不要 `reset`。

合并、rebase、cherry-pick 产生冲突时，同样停止并列出路径。不要自行解决后再推送。用户给出每一处的取舍之后，再按该取舍修改，并在提交说明里写明这是按用户取舍完成的冲突合并。

推送期间发现远程分支比本地超前：停止。先 `git fetch` 查看远程新增了什么，向用户报告。不要 `pull` 时强行覆盖本地，不要 force-push。
