# PR 标题、描述模板与创建条件

准备创建 PR，或判断这次是否应该创建 PR 时，阅读本文件。本文件是 `team-git-workflow` 的 PR 规则。入口与决策顺序在 `skills/team-git-workflow/SKILL.md`。

默认不创建 PR。直推授权覆盖本次交付时，禁止创建 PR。

## 创建条件

同时不处于直推授权时，下列三条任一成立才创建 PR：

1. 用户要求评审（review）。
2. 用户要求合入受保护分支。`main` 与 `master` 是受保护分支。用户另外点名的受保护分支同样算。
3. 用户明确说开 PR，或明确说创建 pull request。

三条都不成立时，不要创建 PR，也不要创建草稿 PR。

用户要求合入受保护分支时，用侧分支加 PR 完成合入。不要把指定工作分支直接合并进 `main` 或 `master`，除非用户明确要求在本地执行合并，并且点名了目标分支。

直推授权与「开 PR」同时出现时，先读 `workflow-examples.md`。仍不能决定则询问。不要既推送又开 PR。

## 分支

开 PR 使用侧分支模式，命名与删除见 `branch-rules.md`。PR 的头分支是该侧分支。基分支是用户点名的合入目标。用户说合入受保护主干但没有在 `main` 与 `master` 之间点名时，询问目标，不要自行选 `main`。

PR 合入之后，删除该侧分支的本地与远程引用。

## 标题

标题写明改了什么，标准与 `commit-rules.md` 的主题行相同：祈使句或中文，点出对象和变更。

拒绝空标题，拒绝只有 `update` / `fix` 及 `commit-rules.md` 所列空洞短语的标题。`validate-pr.py` 用 `validate-commit-msg.sh` 检查标题。标题通过脚本之后，仍要确认读者能看出改动对象。

## 正文模板

ALWAYS 使用下列二级标题。三段都要出现，顺序保持不变。每段写成完整句子或清单，不要只留标题。

```markdown
## 改了什么

- <对象>：<变更>。需要时补一句范围。

## 如何验证

1. <可执行的检查>。预期：<可观察的结果>。

## 链接

- <issue、规格、任务或提交的 URL；没有则写「无」>
```

三段的要求：

| 段 | 写什么 | 不合格 |
|----|--------|--------|
| 改了什么 | 这次行为、文档或规则的变化。点出对象。 | 空段、`TBD`、`update`、`更新代码` |
| 如何验证 | 读者能执行的命令、页面或阅读路径，以及预期结果。 | 空段、`TBD`、`测试一下` |
| 链接 | 相关 issue、规格、任务、提交。没有相关链接时写「无」。 | 空段、只有标题没有正文 |

英文标题可以被脚本接受，含义与中文三段一一对应：`What changed` 或 `Summary`；`How to verify` 或 `Test plan`；`Links` 或 `References`。面向本仓库的 PR 使用上面的中文模板。

## 校验脚本

创建 PR 之前运行：

```bash
skills/team-git-workflow/scripts/validate-pr.py \
  --title "Add team-git-workflow skill" \
  --body-file /path/to/pr-body.md
```

也可以用 `--title-file` 与 `--body`。标题与正文必须各有一处来源。

脚本检查：

- 标题非空，且能通过 `validate-commit-msg.sh` 的空洞说明检查。
- 正文含有上述三段二级标题（中文或对应英文别名）。
- 「改了什么」与「如何验证」有实质内容。`TODO`、`TBD`、`...`、`N/A`、`待定`、`待补充` 视为空。
- 「链接」非空。内容为「无」「none」「无相关链接」时通过。

退出码：`0` 通过；`1` 有缺项。失败信息写在标准错误，一次列出全部问题。

脚本未接入 CI 时，仍按模板填写。不要因为脚本没挂上就省略三段。脚本通过之后再调用创建 PR 的工具。直推任务不要运行创建动作；标题正文检查只在「创建条件」成立时使用。
