# PR 标题、正文与创建条件

准备创建、更新、合入或关闭 PR 时阅读本文件。决策顺序在 `SKILL.md`。仓库的 PR 模板和标题约定优先于这里的默认格式。

没有用户授权，并且仓库政策也没有要求 PR 时，不要创建 PR。Izelzzz/izel-skill 上，用户已经授权推送到 `feature/global` 并且不要 PR 时，禁止创建或更新 PR。见 `workflow-examples.md`。

## 标题

仓库没有标题约定时：

```text
<type>: <short description>
```

类型与 `commit-rules.md` 相同：`feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`perf`、`build`、`ci`。可以写成带 scope 的 `<type>(<scope>): <short description>`。标题描述 diff 里的实际改动，并遵守提交说明里对笼统措辞和编造工单号的限制。

## 正文

仓库提供了 PR 模板时，填那个模板。不要另起一套标题把模板里的必填项盖掉。

仓库没有模板时，ALWAYS 写入下面三节，标题使用中文或对应的英文。有限制、兼容性或发布注意时，再加上「风险与说明」。存在已经核实的工单时，再加上「相关问题」。不适用的节直接省略。不要写 N/A、TBD 或「无」，除非该仓库的模板强制保留那个标题。

```markdown
## 摘要

<改了什么？为什么需要？>

## 变更

- <主要实现变化>

## 验证

- <跑过的测试或检查>：<实际结果>
- 未测：<没跑的项目与原因>

## 风险与说明

<仅在有限制、兼容性或发布注意时保留本节>

## 相关问题

<仅写已核实的工单号或链接>
```

英文标题与中文一一对应：`Summary`、`Changes`、`Validation`、`Risks and Notes`、`Related Issues`。

写作要求：

- 面向评审，简短，写事实。
- 不要只把提交说明按时间顺序重抄一遍。说明这些提交合在一起改变了什么。
- 没运行的测试不要写成通过。验证节写出命令和结果；没跑就写没跑。
- 还没核实的假设，明确标成假设。
- 相关问题只放你已经在工单系统或仓库里看到的编号。不要编造，不要把猜测的编号写进去凑格式。

## 创建之前

逐项核对：

1. 源分支和目标分支就是用户要求的那一对。目标不清楚时询问，不要自行选定 `main`。
2. PR diff 只包含预定改动。用户的无关改动还在工作区时，不要让它们进入源分支的提交。
3. 仓库要求的测试已经运行，或者验证节写明了没测什么。
4. diff 和提交里没有密钥、凭据或环境文件。
5. 标题和正文与 diff 一致，没有描述未包含的改动。
6. 标签、评审人和关联工单符合仓库要求，且工单号已核实。
7. 同一源分支上没有已经打开的重复 PR。有则更新原 PR，不要再开一个，除非用户要求新的 PR。

使用默认正文时，创建前运行：

```bash
scripts/validate-pr.py \
  --title "fix: refresh oauth tokens before expiry" \
  --body-file /path/to/pr-body.md
```

也可以用 `--title-file` 与 `--body`。标题和正文各自只能有一个来源。

脚本检查标题是否符合默认提交格式，并检查「摘要」「变更」「验证」三节有实质内容。可选的两节出现时，也不能是占位符。退出码 `0` 通过；`1` 有缺项，全部问题写在标准错误。

脚本通过之后再调用创建 PR 的工具。脚本没接入 CI 时，仍然按本节填写。

## 创建、更新、合入与关闭

这四件事都需要本轮授权，并且要符合仓库政策。用户要求「做完这项任务」不等于授权合入。没有授权时，不要自动合入，也不要自动关闭。

创建请求发出之后：

- 核实 PR 确实存在。
- 报告工具返回的真实 URL、源分支和目标分支。
- 创建失败时报告失败和原因。不要编造 URL，不要把「命令已发出」写成「PR 已打开」。

合入同样要在合入完成后核对合并结果。合入失败就报告失败。不要为了合入而绕过分支保护或钩子。
