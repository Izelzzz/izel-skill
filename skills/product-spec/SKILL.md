# 产品方案（PRD）

产品规格是供建造者使用的活文档。他人能够据此开发并验收，方可定稿。建议在原则审查之后使用；必要时再补充哲学审查与调研。业务背景或用户问题仍不清晰时，应先完成原则或调研，不得编写缺乏依据的规格。

方案须包含下列九段。缺少任一段，不得定稿。

```markdown
# <方案标题>

## 1. 业务背景
说明为何实施、为何此时实施，以及成功状态的定义。

## 2. 用户故事
作为 [角色]，在 [场景] 下，需要 [能力]，以便 [价值]。

## 3. 流程与路径
主路径与分支；复杂业务须附业务流程图。

## 4. 功能清单
功能与逻辑说明；涉及接口或数据模型的技术备注，须先与工程对齐后再写入。

## 5. 产品预期
用户获得方案后应达到的效果；存在用户界面时，须附原型或线上演示。

## 6. 边界与异常
权限、空态、失败、超时重试、重复提交、回滚、与外部系统不一致等；每条须有预期行为。

## 7. 验收标准
可判定：给定条件 → 执行动作 → 可观察结果（含数据与界面或 API）。

## 8. 术语表
正文领域术语的统一定义；必要时说明「不包含何种含义」。

## 9. 决策日志
时间 | 变更点 | 理由 | 决策人
```

未知项标注为 `TBD`，并记录补充责任人与期限。

用户故事描述意图，不描述实现方式；每个故事至少对应一条验收标准。存在多角色、多状态或较多分支时，须提供业务流程图与用户路径。存在用户界面时，须提供原型或线上演示。纯 API 或无界面时，在产品预期中写明调用方效果，界面项标注不适用。涉及接口或数据模型的技术备注，须先与工程对齐再写入功能清单；已触发上述要求却缺少图示或原型时，不得定稿。

验收标准须能判定通过或失败：给定前置条件、执行动作，并写出可观察的数据、界面或 API 结果。不得使用「体验良好」「尽量快速」「用户满意」等无法核对的表述，除非同时给出可观察的代理指标。边界与异常至少覆盖无权限、无数据、部分失败、超时重试、重复提交、回退撤销、与外部系统不一致；缺少预期行为的异常视为缺口。范围、流程或验收一旦变更，须追加至决策日志，禁止静默修改规格。

定稿前确认：九段齐全；故事可映射至验收标准；复杂业务具备流程说明；存在界面则具备原型或演示；技术备注已对齐或无技术备注；异常均有预期行为；验收标准可判定；术语表覆盖正文；若有变更则决策日志已更新；`TBD` 已清除或已指定责任人与截止日期。任一项未满足时，不得声明定稿或可开发，仅列出缺口。工程无法对齐技术备注时，在功能清单中将该项标为阻塞，并保持不定稿。
