# 产品方案规范

## 使用时机

当任务需要以下产物时，使用本 skill：

- 产品方案、PRD 或等价规格。
- 方案开发可行性评审。
- 方案范围、流程或验收条件发生变化。

推荐顺序：product-design-principles；按需要使用 product-design-philosophy；按需要使用 product-research；最后使用本 skill。

开始时写明：`正在使用 product-spec 编写或评审产品方案。`

## 执行流程

### 1. 建立文档骨架

| # | 章节 | 要求 |
|---|------|------|
| 1 | 业务背景 | 为什么要做这个需求 |
| 2 | 用户故事 | 作为某角色，在某场景，要解决某问题 |
| 3 | 业务流程图 | 复杂业务 MUST 有流程图与用户路径 |
| 4 | 功能清单 | 功能与逻辑清晰；技术实现备注 MUST 先取得工程确认 |
| 5 | 产品预期 | 用户效果；有 UI 则 MUST 有原型或线上 demo |
| 6 | 边界与异常 | 闭环：权限、空态、失败、并发、回滚等 |
| 7 | 验收标准 | 故事可完成、数据正确、体验达预期；须可测 |
| 8 | 术语表 | 领域术语统一定义 |
| 9 | 方案变更决策记录 | 时间 + 理由 |

按以下九章建立文档。未知内容写 `TBD`，并在文档末尾登记负责人和截止时间：

```markdown
# <方案标题>

## 1. 业务背景
- 问题：
- 为什么现在做：
- 成功看起来像什么：

## 2. 用户故事
| ID | 作为… | 在…场景 | 我要… | 以便… |
|----|-------|---------|-------|-------|

## 3. 业务流程图 / 用户路径
- 复杂度：简单 / 复杂
- 复杂则附：流程图链接或粘贴；主路径；分支路径

## 4. 功能清单
| ID | 功能 | 逻辑说明 | 技术备注（已取得工程确认？是/否） |
|----|------|----------|--------------------------------|

## 5. 产品预期
- 用户拿到后应达到的效果：
- UI：原型/demo 链接：（无 UI 则写 N/A）

## 6. 边界与异常场景
| 场景 | 预期行为 | 负责人 |
|------|----------|--------|

## 7. 验收标准
| 故事/功能 ID | 验收条件（可测） | 数据预期 | 体验预期 |
|--------------|------------------|----------|----------|

## 8. 术语表
| 术语 | 定义 | 非含义 |
|------|------|--------|

## 9. 方案变更决策记录
| 时间 | 变更点 | 理由 | 决策人 |
|------|--------|------|--------|
```

### 2. 编写用户故事

格式：

> 作为 **[角色]**，在 **[场景]** 下，我想要 **[能力]**，以便 **[价值]**。

规则：

- 每个故事 MUST 能映射到至少一条验收标准。
- MUST NOT 把技术方案写进故事（故事描述意图，不描述实现）。

### 3. 判断流程图与 UI 交付物

| 条件 | MUST |
|------|------|
| 多角色、多状态、或分支 ≥ 3 | 业务流程图 + 用户路径 |
| 有用户界面 | 原型图或线上 demo |
| 纯 API / 无 UI | 产品预期写清调用方效果；UI 项标 N/A |
| 技术备注涉及接口或数据模型 | 先取得工程确认，再写入功能清单 |

无图或无原型却触发上表时，完整性检查失败，不能定稿。

### 4. 编写功能规则与验收标准

每项功能写清输入、前置条件、处理规则、输出、状态变化、权限、数据来源和失败结果。

技术实现备注使用 `已确认`、`待确认` 或 `不适用`。`待确认` 项必须有工程负责人和截止时间。

每条验收标准必须包含输入或前置条件、执行动作和可观察结果。

好的写法：

- 给定输入 / 前置条件
- 执行动作
- 期望结果（含数据与界面/API 可观察点）

避免：

- 「体验良好」「尽量快」「用户满意」等不可测词，除非附带可观察代理指标

检查：

- 用户故事是否能完成
- 数据是否被正确处理
- 体验是否达到预期（对照产品预期与原型）

### 5. 编写边界与异常

至少扫描：

- 无权限 / 无数据 / 部分失败
- 超时、重试、重复提交
- 状态回退与撤销
- 与外部系统不一致

每个场景都写预期行为、用户可见结果和责任人。没有处理规则的场景计为缺口。

### 6. 记录方案变更

任何范围、流程、验收变更 MUST 追加到第 9 章：

- 时间
- 变更点
- 理由
- 决策人

不要静默修改已评审内容。

## 完整性闸门

- [ ] 九章齐全
- [ ] 用户故事可映射到验收标准
- [ ] 复杂业务已有流程与路径
- [ ] 有 UI 则有原型或 demo
- [ ] 技术备注已取得工程确认（或无技术备注）
- [ ] 边界与异常有预期行为
- [ ] 验收标准可测
- [ ] 术语表覆盖正文术语
- [ ] 若有变更，决策记录已更新
- [ ] TBD 均有主人与截止日期，或已清除

全部通过时，状态写为“方案可进入开发评审”。存在缺口时，状态写为“需要补充”，并列出缺口、负责人和截止时间。缺口未关闭时，不写“方案定稿”或“可开发”。

## 完成标准

- 文档满足完整性清单
- 验收标准可被测试或人工按步骤判定
- 变更可追溯

## 停止条件

- 业务背景或用户问题不清时，退回 product-design-principles 或 product-research。
- 工程拒绝确认技术备注时，保留阻塞状态并停止定稿。
