# 产品方案规范

## 何时使用

在以下情况 MUST 使用本 skill：

- 撰写产品方案、PRD 或等价规格
- 评审方案是否可开发、可验收
- 方案发生变更，需要记决策日志

建议顺序：原则检查 →（按需）哲学打磨 →（按需）调研 → **本 skill 出规格**。

开始时宣布：正在使用 product-spec 编写或评审产品方案。

## 必含九段

方案 MUST 包含以下章节。缺一不可定稿。

| # | 章节 | 要求 |
|---|------|------|
| 1 | 业务背景 | 为什么要做这个需求 |
| 2 | 用户故事 | 作为某角色，在某场景，要解决某问题 |
| 3 | 业务流程图 | 复杂业务 MUST 有流程图与用户路径 |
| 4 | 功能清单 | 功能与逻辑清晰；技术实现备注 MUST 先与工程对齐 |
| 5 | 产品预期 | 用户效果；有 UI 则 MUST 有原型或线上 demo |
| 6 | 边界与异常 | 闭环：权限、空态、失败、并发、回滚等 |
| 7 | 验收标准 | 故事可完成、数据正确、体验达预期；须可测 |
| 8 | 术语表 | 领域术语统一定义 |
| 9 | 方案变更决策记录 | 时间 + 理由 |

## Step 1 — 建文档骨架

复制模板并填空。未知项写 `TBD`，并列入缺口表。

```markdown
# <方案标题>

## 1. 业务背景
- 问题：
- 为什么现在做：
- 成功看起来像什么：

## 2. 用户故事
| ID | 作为… | 在…场景 | 我要… | 以便… |
|----|-------|---------|-------|-------|

## 3. 业务流程图 / 用户路径
- 复杂度：简单 / 复杂
- 复杂则附：流程图链接或粘贴；主路径；分支路径

## 4. 功能清单
| ID | 功能 | 逻辑说明 | 技术备注（已与工程对齐？是/否） |
|----|------|----------|--------------------------------|

## 5. 产品预期
- 用户拿到后应达到的效果：
- UI：原型/demo 链接：（无 UI 则写 N/A）

## 6. 边界与异常场景
| 场景 | 预期行为 | 负责人 |
|------|----------|--------|

## 7. 验收标准
| 故事/功能 ID | 验收条件（可测） | 数据预期 | 体验预期 |
|--------------|------------------|----------|----------|

## 8. 术语表
| 术语 | 定义 | 非含义 |
|------|------|--------|

## 9. 方案变更决策记录
| 时间 | 变更点 | 理由 | 决策人 |
|------|--------|------|--------|
```

## Step 2 — 写用户故事

格式：

> 作为 **[角色]**，在 **[场景]** 下，我想要 **[能力]**，以便 **[价值]**。

规则：

- 每个故事 MUST 能映射到至少一条验收标准。
- MUST NOT 把技术方案写进故事（故事描述意图，不描述实现）。

## Step 3 — 判断是否需要图与原型

| 条件 | MUST |
|------|------|
| 多角色、多状态、或分支 ≥ 3 | 业务流程图 + 用户路径 |
| 有用户界面 | 原型图或线上 demo |
| 纯 API / 无 UI | 产品预期写清调用方效果；UI 项标 N/A |
| 技术备注涉及接口或数据模型 | 先与工程对齐，再写入功能清单 |

无图/无原型却触发上表 → 完整性失败，不得定稿。

## Step 4 — 写可测验收标准

每条验收标准 MUST 可判定通过/失败。

好的写法：

- 给定输入 / 前置条件
- 执行动作
- 期望结果（含数据与界面/API 可观察点）

避免：

- 「体验良好」「尽量快」「用户满意」等不可测词，除非附带可观察代理指标

检查：

- 用户故事是否能完成
- 数据是否被正确处理
- 体验是否达到预期（对照产品预期与原型）

## Step 5 — 边界与异常闭环

至少扫描：

- 无权限 / 无数据 / 部分失败
- 超时、重试、重复提交
- 状态回退与撤销
- 与外部系统不一致

每条异常 MUST 有预期行为。无行为 = 缺口。

## Step 6 — 变更时记决策日志

任何范围、流程、验收变更 MUST 追加到第 9 章：

- 时间
- 变更点
- 理由
- 决策人

MUST NOT 静默改规格。

## Step 7 — 完整性清单（定稿闸门）

- [ ] 九章齐全
- [ ] 用户故事可映射到验收标准
- [ ] 复杂业务已有流程与路径
- [ ] 有 UI 则有原型或 demo
- [ ] 技术备注已与工程对齐（或无技术备注）
- [ ] 边界与异常有预期行为
- [ ] 验收标准可测
- [ ] 术语表覆盖正文术语
- [ ] 若有变更，决策记录已更新
- [ ] TBD 均有主人与截止日期，或已清除

任一项未勾 → MUST NOT 声称「方案定稿 / 可开发」。报告缺口。

## 完成标准

- 文档满足完整性清单
- 验收标准可被测试或人工按步骤判定
- 变更可追溯

## 停止条件

- 业务背景或用户问题不清 → 退回原则/调研，不写假规格
- 工程拒绝对齐技术备注 → 功能清单中技术列标阻塞，不定稿
