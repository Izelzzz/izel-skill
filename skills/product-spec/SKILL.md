# 产品方案（PRD）

规格是给建造者用的活文档。写完别人能开发、能验收，才叫定稿。

建议顺序：原则 →（按需）哲学 →（按需）调研 → **本 skill 出规格**。

## 何时用

- 撰写产品方案、PRD 或等价规格
- 评审方案能不能开发、能不能验收
- 方案改了，需要留下决策痕迹

业务背景或用户问题还不清，先回去过原则 / 调研。不要写假规格。

## 九段骨架

缺一段就不定稿。复杂业务和有 UI 的方案，图与原型有硬要求（见下）。

```markdown
# <方案标题>

## 1. 业务背景
为什么做、为什么现在做、成功长什么样。

## 2. 用户故事
作为 [角色]，在 [场景] 下，我想要 [能力]，以便 [价值]。

## 3. 流程与路径
主路径；分支；复杂业务附流程图。

## 4. 功能清单
功能 + 逻辑说明；涉及接口/数据模型的技术备注，先和工程对齐再写。

## 5. 产品预期
用户拿到后应达到的效果；有 UI 则附原型或线上 demo。

## 6. 边界与异常
权限、空态、失败、超时重试、重复提交、回滚、与外部不一致……每条有预期行为。

## 7. 验收标准
可测：给定条件 → 动作 → 可观察结果（含数据与界面/API）。

## 8. 术语表
正文里的领域词，统一定义；必要时写「不是什么」。

## 9. 决策日志
时间 | 变更点 | 理由 | 决策人
```

未知写 `TBD`，并记住谁来补、何时补。

## 怎么写关键段

**用户故事**  
描述意图，不写实现。每个故事至少映射一条验收标准。

**流程与原型 — 何时必须有**

- 多角色、多状态、或分支 ≥ 3 → 要业务流程图和用户路径
- 有用户界面 → 要原型或线上 demo
- 纯 API / 无 UI → 产品预期写清调用方效果，UI 项标 N/A
- 技术备注涉及接口或数据模型 → 先和工程对齐，再写入功能清单

触发了上表却没有图/原型 → 完整性失败，不定稿。

**验收标准要可测**  
坏例子：「体验良好」「尽量快」「用户满意」。  
好例子：前置条件 + 动作 + 期望的数据/界面/API 结果。  
验收时核对：故事能否完成、数据是否正确、体验是否对照预期与原型。

**边界与异常**  
扫一遍无权限、无数据、部分失败、超时重试、重复提交、回退撤销、外部不一致。没有预期行为的异常 = 缺口。

**决策日志**  
范围、流程、验收一变，就追加第 9 段。禁止静默改规格。

## 定稿前自检

- 九段齐全
- 故事能映射到验收
- 复杂业务有流程；有 UI 有原型/demo
- 技术备注已对齐（或没有技术备注）
- 异常有预期行为
- 验收可测
- 术语表覆盖正文
- 有变更则日志已更新
- TBD 有主人与截止日期，或已清掉

任一项不过 → 不要说「定稿 / 可开发」。列出缺口。

## 完成时

- 自检全过
- 验收标准可被测试或按步骤人工判定
- 变更可追溯

## 何时停

- 背景或用户问题不清 → 退回原则/调研
- 工程拒绝对齐技术备注 → 功能清单技术列标阻塞，不定稿
