# 产品设计原则

## 何时使用

在以下任一情况 MUST 使用本 skill：

- 提出新功能、新产品或重大改版
- 评审、批准或拒绝产品方案
- 用户要求检查方案是否「站得住」

## 硬性规则

1. 提出或批准方案前，MUST 跑完下方四原则检查清单。
2. 每个原则 MUST 写出：结论（通过 / 缺口 / 未知）、证据、待办。
3. 存在未认领的缺口时，MUST NOT 使用「可上线」「方案完成」「没问题」等表述。
4. 缺口 MUST 标明责任人或决策人，或明确「暂缓，等确认」。

开始时宣布：正在使用 product-design-principles 做四原则检查。

## 执行步骤

### Step 1 — 收集输入

先记录：

- 目标用户与场景
- 提出的需求或方案摘要
- 已知目标与成功指标（若有）
- 已知约束（时间、资源、合规）

缺关键输入时，先问清楚再继续。不要猜。

### Step 2 — 第一性原理

核心问题：**我们为什么要做这件事？**

逐项回答：

1. 真实用户问题是什么？（不是用户提出的解决方案）
2. 哪些是事实？哪些是假设？哪些是行业惯例？
3. 从目标倒推：必要条件有哪些？
4. 「以前一直这么做」是否被当成理由？若是，MUST 剔除。

输出模板：

```
【第一性原理】
真实问题：
事实：
假设：
惯例（非理由）：
倒推必要条件：
结论：通过 / 缺口 / 未知
缺口与认领：
```

### Step 3 — 奥卡姆剃刀

核心问题：**哪些东西其实不需要？**

检查是否无必要地引入：

- 新概念
- 新系统状态
- 新功能
- 新流程
- 新抽象层

规则：

- 如无必要，MUST NOT 增加上述任何一项。
- MUST NOT 为了假简洁删除必要能力。
- 保留的复杂性 MUST 有明确理由（一句话）。

输出模板：

```
【奥卡姆剃刀】
可删除项：
必须保留项 + 理由：
结论：通过 / 缺口 / 未知
缺口与认领：
```

### Step 4 — 正确的业务抽象

核心问题：**业务是否建模正确？**

列出：

1. 核心实体、属性、关系、约束
2. 业务概念 vs 技术实现（表结构、现有代码不得反向定义业务）
3. 状态转换、权限、边界、异常路径

规则：

- 抽象 MUST 反映真实业务规律。
- MUST NOT 为抽象而抽象。

输出模板：

```
【业务抽象】
实体 / 属性 / 关系 / 约束：
状态与权限：
边界与异常：
业务 vs 技术分离：是 / 否（说明）
结论：通过 / 缺口 / 未知
缺口与认领：
```

### Step 5 — 正确衡量 ROI

核心问题：**这件事值得投入吗？**

评估：

1. 用户价值
2. 业务收益
3. 实现成本
4. 长期维护成本
5. 不做的代价
6. 其他方案的机会成本

规则：

- MUST 覆盖短期收入以外的维度：降风险、提效率、战略价值。
- MUST 给出可观测指标来验证预期。MUST NOT 只凭感觉判成功。

输出模板：

```
【ROI】
价值：
成本：
不做代价：
机会成本：
验证指标：
结论：通过 / 缺口 / 未知
缺口与认领：
```

### Step 6 — 汇总闸门

汇总四原则结果：

| 原则 | 结论 | 未闭合缺口 | 认领人 |
|------|------|------------|--------|
| 第一性原理 | | | |
| 奥卡姆剃刀 | | | |
| 业务抽象 | | | |
| ROI | | | |

闸门：

- 四项均为「通过」→ 可继续细化方案或进入 product-spec。
- 任一项为「缺口」且无人认领 → STOP。报告缺口。禁止「可上线」表述。
- 任一项为「未知」→ STOP。先补证据或标为假设并认领验证计划。

## 完成标准

- 四原则均有书面结论与证据
- 全部缺口已认领或明确暂缓
- 未对未过闸方案声称可交付

## 停止条件

- 关键事实缺失且用户无法补充 → 输出「阻塞清单」，停止设计推进
- 用户明确要求跳过检查 → 记录风险后可继续，但 MUST 标注「未过原则闸门」
