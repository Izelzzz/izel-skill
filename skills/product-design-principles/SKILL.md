# 产品设计原则

先把方案想清楚，再谈实现。这个 skill 教你怎么质疑 brief，而不是怎么填表。

## 何时用

- 有人提出新功能、新产品或重大改版
- 你要评审、批准或拒绝一个方案
- 用户问「这个方案站得住吗」

原则没过关，不要跳到哲学打磨或写 PRD。

## 你要怎么做

用对话把问题挖出来。每道闸门问完，用几句白话写下发现。不要甩一堆空模板。

缺关键事实就问。不要猜。猜出来的东西标成假设。

## 四道闸门

按顺序过。任一道有未闭合缺口，就停在这里，先处理缺口。

### 1. 第一性原理 — 为什么要做

问自己，也问对方：

1. 真实用户问题是什么？把「用户要的解决方案」和「用户真正卡在哪」分开。
2. 哪些是事实？哪些是假设？哪些只是「以前一直这么做」？
3. 从目标倒推：没有哪些条件，这件事根本不成立？
4. 「行业惯例」有没有被当成理由？有的话，丢掉它，重新论证。

写下来：真实问题、事实、假设、必须成立的条件。缺口用白话说清楚。

### 2. 奥卡姆 — 哪些其实不需要

检查方案有没有多出来的：

- 概念
- 系统状态
- 功能
- 流程步骤
- 抽象层

能删就删。删之前问一句：删掉会不会丢掉用户真正需要的能力？会，就留，并写一句为什么必须留。

假简洁不算过关。把能力砍没了，然后说「很简单」，是失败。

### 3. 业务模型 — 业务有没有建模对

先谈业务，再谈技术。表结构、现有代码、接口形状，不能反向定义业务。

弄清楚：

- 核心实体、关系、约束
- 状态怎么转
- 谁有什么权限
- 边界和异常路径是什么

抽象要反映真实业务规律。不要为抽象而抽象。

如果技术约束在逼业务变形，把冲突说出来，让人做选择。不要假装没有冲突。

### 4. ROI — 值不值得做

看这几面，不要只看短期收入：

- 用户能得到什么价值
- 业务能得到什么收益（含降风险、提效率、战略位置）
- 实现成本 + 长期维护成本
- 不做的代价
- 做别的事的机会成本
- 用什么可观测指标证明预期实现了

没有验证指标，就还没有闭合这道闸。感觉不能当证据。

## 输出

检查结束后，给一段短发现，不要九宫格报表。建议结构：

```
结论：可继续 / 有缺口，先停
过关的：……
没过的：……（每条缺口 + 谁来补 + 补什么）
假设清单：……
下一步：……
```

有未认领的缺口时，禁止说「可上线」「方案完成」「没问题」。可以说「方向大致对，但这些缺口不补就不能定」。

## 完成时

- 四道闸门都有结论和依据
- 缺口都有认领人，或明确写「暂缓，等确认」
- 没有对未过关方案声称可交付

## 何时停

- 关键事实缺失，对方也补不上 → 列出阻塞项，停止推进设计
- 对方坚持跳过 → 可以继续，但必须标明「未过原则闸门」，并写出风险
