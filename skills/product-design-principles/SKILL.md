# 产品设计原则

## 使用时机

当任务满足以下任一条件时，使用本 skill：

- 提出新产品、新功能或重大改版。
- 评审、批准、拒绝或比较产品方案。
- 用户要求判断方案是否成立、是否值得投入。

开始时写明：`正在使用 product-design-principles 进行原则检查。`

## 输入

收集以下内容。缺少关键内容时，停止判断并列出待补信息：

- 目标用户和使用场景。
- 用户问题或方案摘要。
- 目标与成功指标。
- 时间、人员、技术、法规和预算限制。
- 已知事实、假设和来源。

## 执行流程

### 1. 检查第一性原理

回答以下问题：

- 用户遇到的真实问题是什么？
- 哪些内容有证据？哪些内容仍是假设？
- 从目标倒推，完成任务需要哪些必要条件？
- 是否把历史做法当成理由？若有，移除该理由并重新判断。

输出：

```text
【第一性原理】
真实问题：
事实：
假设：
历史做法：
必要条件：
结论：通过 / 缺口 / 未知
缺口负责人：
验证动作与截止时间：
```

### 2. 检查必要复杂度

逐项检查以下内容：

- 新概念。
- 新状态。
- 新功能。
- 新流程。
- 新抽象层。

每一项都写出保留理由。没有必要理由的内容，列入删除清单。保留内容必须直接服务于用户任务、业务约束或可观测指标。

输出：

```text
【必要复杂度】
可移除内容：
必须保留内容与理由：
结论：通过 / 缺口 / 未知
缺口负责人：
验证动作与截止时间：
```

### 3. 检查业务模型

描述真实业务对象与关系：

- 核心实体、属性和关系。
- 状态变化与触发条件。
- 权限、责任和边界。
- 空数据、失败、重复请求和外部系统异常。
- 业务概念与技术实现的分界。

技术表结构、现有代码和接口只能作为证据，不能单独定义业务含义。

输出：

```text
【业务模型】
实体与关系：
状态与触发条件：
权限与责任：
边界与异常：
业务概念和技术实现是否分开：是 / 否 / 未知
结论：通过 / 缺口 / 未知
缺口负责人：
验证动作与截止时间：
```

### 4. 检查投入回报

至少评估以下项目：

- 用户价值。
- 业务收益。
- 实现成本。
- 长期维护成本。
- 暂缓或不做的代价。
- 其他方案的机会成本。
- 降低风险、提高效率或形成长期能力的价值。

每个预期都绑定一个可观察指标、目标值和观察周期。只有主观判断时，结论写为“未知”。

输出：

```text
【投入回报】
价值：
成本：
暂缓代价：
机会成本：
指标、目标值与观察周期：
结论：通过 / 缺口 / 未知
缺口负责人：
验证动作与截止时间：
```

### 5. 汇总决策闸门

输出以下内容：

```text
【原则检查结果】
第一性原理：通过 / 缺口 / 未知
必要复杂度：通过 / 缺口 / 未知
业务模型：通过 / 缺口 / 未知
投入回报：通过 / 缺口 / 未知

未闭合缺口：
负责人或决策人：
下一步动作：
最终状态：继续细化 / 补充证据 / 暂缓
```

决策规则：

- 四项均为“通过”时，允许进入方案细化或 product-spec。
- 任一项为“缺口”且没有负责人时，停止推进并输出阻塞清单。
- 任一项为“未知”时，先补证据，或明确验证计划与负责人。
- 存在未闭合缺口时，不使用“可上线”“方案完成”“可以开发”等结论。

## 完成标准

- 四项检查都有结论和证据。
- 每个缺口都有负责人、动作和截止时间，或明确暂缓。
- 每个成功预期都有可观察指标。
- 汇总状态符合决策规则。

## 停止条件

关键事实无法取得时，输出阻塞清单并停止方案判断。用户要求跳过检查时，记录跳过项目、已知风险和决策人，再继续执行。
