# 产品设计哲学

`worth-it-or-not`（值不值得做）回答「是否应当做」。本 skill 回答「应做成何种形态，方可被理解、被信任并持续使用」。方向未定时先做值不值得做审查，否则会在错误问题上打磨产品形态。

## 对内判断（默认不展示）

在内部推理中按场景选用方法；不适用项跳过并在内部记清理由。已跳过的项，事后不要视为已满足。审查过程与方法选用表留在内部推理，**默认不写入对用户的回复**。仅当用户明确要求「展开审查过程」「写出各项判定」时，才输出完整纪要。

### 确认场景并选用方法

先确认：新产品还是增量功能；是否存在首次接触路径；是否为内部工具；是否涉及支付或隐私等信任敏感场景。默认指引：

| 场景 | 通常启用 | 常可跳过 |
|------|----------|----------|
| 新产品 / 新功能首次对外 | 少即是多、控制预期、叙事 | — |
| 成熟产品增量 | 少即是多、控制预期 | 无新用户路径时可跳过叙事 |
| 内部工具 | 少即是多、控制预期 | 叙事 |
| 信任敏感（支付、隐私、资金） | 长期信任、控制预期 | 按实际再选其余项 |

先从完整体验与产品形态判断，再决定对外粒度：用户问的是产品结构、信息架构或用户路径时，方案写到路径与结构；用户问的是某一页或某一句时，方案写到该页文案。粒度与所问一致。

### 少即是多

判断用户完成主任务需理解的概念数量。检查主路径中的概念、文案、步骤与选项能否减少，且不损害必要能力。概念堆叠会抬高理解成本；若成本过高，列出可删除或可合并项，落到对外方案的具体取舍。

### 长期信任

判断设计是在积累信任与长期收益，还是以透支信任换取短期刺激。透支型设计短期有数据、长期伤品牌与留存；若属透支，改成可积累的设计，并写成可执行方案。

### 控制预期

判断对外表述是否不超过真实能力，真实问题是否表述清楚。承诺须可兑现、可核验。空洞叙事或过度承诺会在用户第一次碰壁时毁掉信任；若存在此类问题，在方案中改为可核对的范围或表述。

### 叙事与 onboarding

判断新用户能否在较短路径内理解产品为其解决的问题，以及价值、场景与下一步是否清晰。叙事与产品能力脱节时，按所问粒度，在方案中给出路径、信息架构或文案上的具体取舍。

对每个启用的方法，内部以「满足 / 未满足」判定。未满足项必须落到对外方案的具体取舍；缺上下文时才进「还想确认」。不要用模糊的「优先级」替代判断。全部启用项满足后，再进入规格或实现细化。

## 用户可见输出

ALWAYS use this exact structure. 不要输出「方法选用表 + 各项判定 / 证据」式长纪要。不以「结论」「建议修改」作为主交付。

```markdown
# <功能/方向>

## 依据的原则
- …（只用到的原则；一句说明怎么落到本案）

## 方案
### 方案 A（推荐）
…

### 方案 B（备选，可选）
…

## 还想确认（仅缺上下文时）
1. …？
```

写法要求：

- 依据已启用的原则，给出一至两个可执行方案。不评判用户；用产品选项作答。
- 先从完整体验与产品形态出发，再决定本次交付是完整路径或信息架构方案，还是页面级文案。粒度与用户所问一致。
- **依据的原则**只列本案用到的原则。每条一句，说明该原则如何落到这个方案，不复述方法定义。
- **方案**写可执行的产品选项。方案 A 为推荐。无有意义的备选时，省略方案 B，不要为凑结构另造一个。
- **还想确认**仅在缺少上下文、否则无法给出靠谱方案时使用；上下文足够则直接给方案，不为凑齐结构而追问。整节可省略。
- 未满足项未落实到方案之前，不要批准体验定稿。
- 用户明确要求展开审查过程时，可再补完整纪要；默认不补。

## Example

**Input：** 「我们想做个人知识库：笔记、网页剪藏、文件上传、日历、待办、AI 对话全打通，做一个 all-in-one 第二大脑。」

**对外应输出的形态（示意）：**

```markdown
# 个人知识库的产品形态

## 依据的原则
- 少即是多：笔记、网页剪藏、文件与对话收成一条主路径；日历与待办不作为并列产品。
- 叙事与 onboarding：新用户用一份真实材料走完「放入，再找回或追问」，而不是先认识全部模块。
- 控制预期：能力尚未打通前，不以「全能第二大脑」对外承诺。

## 方案
### 方案 A（推荐）
主叙事与主路径收成一件事：把笔记、网页剪藏和上传的文件收进一处，需要时找得到，并能就这些材料继续对话。日历与待办不作为并列产品，不设同级入口；若要用，从材料或对话里带出。Onboarding 只使用一份用户自己的真实材料：放入，再完成一次找回，或基于该材料追问一句。对外暂不称「全能第二大脑」。

### 方案 B（备选，可选）
若方向仍是「第二大脑」，则分期交付。每一期只开放已经可用的能力。日历、待办以及跨入口打通在未完成时写明尚未提供。名称可以保留「第二大脑」，表述停在当期真实能力，不把未完成的能力说成已经打通。

## 还想确认（仅缺上下文时）
1. 第一期要验证的是「找得到材料」，还是「对话能推进下一步」？
```

不要对外展开「少即是多：未满足 / 证据三段」之类纪要，除非用户明确要求展开审查过程。
