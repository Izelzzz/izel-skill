# 产品设计哲学

原则审查回答「是否应当做」。本 skill 回答「应做成何种形态，方可被理解、被信任并持续使用」。方向未定时先做原则审查，否则会在错误问题上打磨体验。

## 对内判断（默认不展示）

在内部推理中按场景选用方法；不适用项跳过并在内部记清理由。已跳过的项，事后不要视为已满足。审查过程与方法选用表留在内部推理，**默认不写入对用户的回复**。仅当用户明确要求「展开审查过程」「写出各项判定」时，才输出完整纪要。

### 确认场景并选用方法

先确认：新产品还是增量功能；是否存在首次接触路径；是否为内部工具；是否涉及支付或隐私等信任敏感场景。默认指引：

| 场景 | 通常启用 | 常可跳过 |
|------|----------|----------|
| 新产品 / 新功能首次对外 | 少即是多、控制预期、叙事 | — |
| 成熟产品增量 | 少即是多、控制预期 | 无新用户路径时可跳过叙事 |
| 内部工具 | 少即是多、控制预期 | 叙事 |
| 信任敏感（支付、隐私、资金） | 长期信任、控制预期 | 按实际再选其余项 |

### 少即是多

判断用户完成主任务需理解的概念数量。检查主路径中的概念、文案、步骤与选项能否减少，且不损害必要能力。概念堆叠会抬高理解成本；若成本过高，列出可删除或可合并项，写成对外的具体改法。

### 长期信任

判断设计是在积累信任与长期收益，还是以透支信任换取短期刺激。透支型设计短期有数据、长期伤品牌与留存；若属透支，改成可积累的设计，并写成可执行修改。

### 控制预期

判断对外表述是否不超过真实能力，真实问题是否表述清楚。承诺须可兑现、可核验。空洞叙事或过度承诺会在用户第一次碰壁时毁掉信任；若存在此类问题，改为可核对的表述。

### 叙事与 onboarding

判断新用户能否在较短路径内理解产品为其解决的问题，以及价值、场景与下一步是否清晰。叙事与产品能力脱节时，给出文案或路径的具体修改。

对每个启用的方法，内部以「满足 / 未满足」判定。未满足项必须落到对外的「建议修改」；缺上下文时才进「还想确认」。不要用模糊的「优先级」替代判断。全部启用项满足后，再进入规格或实现细化。

## 用户可见输出

ALWAYS use this exact structure. 不要输出「方法选用表 + 各项判定 / 证据」式长纪要。

```markdown
# <功能/文案>

## 结论
可定稿 | 建议先改这些

## 建议修改
1. 把「…」改成「…」（理由一句）
2. …

## 还想确认（仅缺上下文时）
1. …？
```

写法要求：

- **结论**一句说清：能定稿就定稿；否则写「建议先改这些」。
- **建议修改**是主交付：每条给出具体改法（原文 → 建议文案，或路径/步骤怎么收），理由控制在一句。用户要的是可执行修改，不是审查过程。
- **还想确认**仅在缺上下文、无法给出靠谱改法时使用；有把握就直接改，不要为了完整而追问。
- 未满足项未改前，不要批准体验定稿。
- 用户明确要求展开审查过程时，可再补完整纪要；默认不补。

## Example

**Input：** 「支付页加一行『极速到账，从未失败』，转化会更好。」

**对外应输出的形态（示意）：**

```markdown
# 支付结果页「极速到账，从未失败」

## 结论
建议先改这些

## 建议修改
1. 把「极速到账，从未失败」改成「支付已提交；工作日通常 2 小时内到账，失败将原路退回并短信通知」（避免绝对化承诺，异常时仍可核对）
2. 结果页补「查看进度」与客服入口，让失败路径可控，而不是制造「零失败」幻觉

## 还想确认
1. 当前真实到账时效与失败率大概是多少？（若已有数据，文案里的时效数字可再收紧）
```

不要对外展开「长期信任：未满足 / 证据三段」之类纪要，除非用户明确要求展开审查过程。
