# 决策记录（decision-record）

把过程中的取舍记成以后的人能看懂、能追溯的记录：为什么这样定、放弃了什么、什么时候定的、谁定的。读者是没参加这次讨论的人，包括几周后的用户自己。

一条记录要让读者不翻聊天记录也能回答三个问题：当时要解决什么问题；最后怎么做；付出了什么代价。

## 1. 什么时候记

要记：

- 用户拍板了一个会影响代码、接口、数据、流程或体验的选择。
- Agent 实现时自己定了设计文档没写到的细节。先列出来请用户确认（第 2 节），确认后再记。
- 新决定推翻或部分推翻旧决策（第 6 节）。
- 用户在讨论中追问，暴露出旧决策没覆盖的情况，并据此补了规则。

不记：

- 只有一种合理做法，或答案由规格、契约、平台限制直接决定。直接照做，在回复里说一句即可。
- 纯措辞、排版、命名的修改，除非它改变了含义。

## 2. 先请用户拍板

决策由用户定。Agent 负责把问题讲清楚、给出建议，不替用户拍板。

**只问真有分歧的事。** 提问前自查：这一条是否存在两个都说得通、且结果不同的做法？如果「本来就应该这样」，不要问，直接按它做并在回复里说明。用户被问到显而易见的问题时，会反问「为什么问这个」。

**每条一行：要定什么、建议怎么做、一句理由。**

```text
要你定的有三件，每条是我的建议：
1. nit 合并那一次模型调用的超时：2 分钟。正常 20 到 60 秒，2 分钟留了 2 到 4 倍余量。
2. 说明审查员的调度：和维度审查员同时跑、同一优先级，最晚第 20 分钟交。它不依赖审查结果，没理由排在后面。
3. 改动说明的核对：不另派模型验证，由程序核对引用的文件和行号。另派验证会让成本翻倍。

同意的不用回；要改哪条，回编号和你的想法。
```

- 每条直接写出建议的做法，不写成「……吗？（是）」这种是非题。用户看到的是一个可以照做的方案，而不是一道选择题。
- 有一个认真考虑过的备选时，在同一行后面补一句「另一种：……，代价是……」。
- 需要背景才能判断的，在清单前用两三句讲清背景，不要把背景塞进每一行。
- 引用旧决策时写清是哪一条的第几项、内容是什么，不要只丢一个编号。例如「D-030 第 5 项：行间评论用隐藏标记去重」。
- 一次请示的事项超过 6 条时，先问会决定后续方向的那几条。

**用户没看懂时，补背景，不催答。** 先讲清这个问题出在哪个流程、不处理会怎样，再重新问。已写进记录的，状态保持「待决定」，等用户确认。

**用户的回答带出新问题时**（比如「部分失败、部分超时算什么」），先说明现在的实际行为，再给建议，然后按同样格式请示。

## 3. 一条记录只管一件事

- **标题就是结论。** 只看列表就能知道定了什么：「同一个 PR 有新推送时，旧审查作废」。不要写成「上下文实现中的小取舍」「审查流水线的六个取舍」这类只说主题的标题。
- **多项共用一个背景和目的，才放在同一条。** 比如「发评论的三条约定」都是为了解决 CI 发评论这一个流程里的问题。背景互不相干的几项，拆成几条。
- **拆分时留痕。** 从旧记录拆出的，在旧记录的结论里写明「第 5、7、8 项已移到 D-033」，新记录的关联里写「从 D-030 第 5、7、8 项拆出」。

## 4. 字段

项目已有决策库时，沿用它的字段和取值。没有时用下面这一套：

| 字段 | 写什么 |
|------|--------|
| 编号 | `D-001` 起递增，作为引用标识；不复用，不重排 |
| 决策 | 一句话结论，即标题 |
| 结论 | 单独读也能看懂的摘要：做法的要点、关键数字；被取代时写被谁取代、哪几项仍有效 |
| 状态 | `待决定` / `已决定` / `已被取代` / `已废弃` |
| 日期 | 拍板的日期 |
| 决策人 | 拍板的人。Agent 提议、用户确认的，写用户 |
| 领域 | 项目自己的分类，例如配置、安全、部署、体验、流程 |
| 关联 | issue、PR、设计文档章节、相关或被取代的决策编号 |

## 5. 正文结构

```markdown
## 背景
## 目的
## 做法
## 为什么这样做
## 代价与后续
```

- **背景：** 先讲清现状和相关流程，让没参加讨论的人能看懂问题出在哪里。流程涉及几个参与方时，附一张流程图（Mermaid）。写清「不处理会出什么问题」，最好带一个具体场景。
- **目的：** 做成什么样算解决。写成能观察到的结果，例如「验证过的发现一条都不丢」。
- **做法：** 具体到可以照着实现：数字、阈值、格式、例子。分情况的写成表格。多项用 ①②③ 编号，方便引用。
- **为什么这样做：** 列出认真考虑过的备选，说明放弃它们的原因。参考了外部做法的，写出处。
- **代价与后续：** 这个做法接受了什么副作用。哪些数字是暂定的，由什么来验证、什么时候再调。

背景和目的不能省。用户连问题都没看懂时，做法写得再细也无法确认。

一条记录有多项、各项问题不同时，每项按「会出什么问题 → 目的 → 做法 → 为什么这样做 → 代价」写，共用的背景放在最前面。

写正文前先读 `references/example.md`，它是一条完整的样板记录，结构、粒度和语气照它写。

## 6. 取代与修改

- **不删旧记录。** 新决定推翻旧决定时，把旧记录状态改为「已被取代」，结论里写明被哪一条取代，哪几项仍然有效。新记录的关联里写「取代 D-028 的『收尾 10 分钟』」。
- **只补细节、方向不变：** 直接更新那一条，在结论里写清补了什么。
- **方向变了：** 新建一条，按上一条处理旧记录。
- **记录格式的要求变了**（比如以后每条都要写背景和目的）：新记录照新格式写；当天新建的顺手补上；更早的问用户要不要回补，不要默默批量改。

## 7. 写法

- **用准确的术语，不用口语比喻。** 「最值钱的先验」改成「按优先级」，并写出优先级顺序。
- **具体。** 写数字、文件、章节号、例子，不写「若干」「适当」「一段时间」。
- **术语第一次出现时解释。** 比如「门禁：开启后，有 🔴 的 PR 不能合入」。
- **区分已定和暂定。** 暂定的数字标出来，写明由哪次评测或哪个 issue 确认。
- **结论与正文一致。** 改了正文，同步改结论字段，反之亦然。

## 8. 落盘

决策记录由两部分组成：一份**决策列表**（每条一行：编号、决策、状态、日期等字段），和每条决策各自的一篇**正文**（第 5 节）。列表用来查找和看状态，正文用来讲清来龙去脉。

记在哪里由用户定：

1. **用户已经说过，或项目里已有决策列表**（Notion 数据库、`docs/decisions/`、`adr/` 目录等）：直接写进去，沿用它的编号和字段。先读最近两三条，对齐格式。
2. **都没有**：第一次记录前先问用户想记在哪里，只问这一次，之后沿用。问的时候给出常见做法和建议，例如：

   ```text
   这个项目还没有决策列表，你想记在哪里？
   - 仓库里的 docs/decisions/（我的建议）：一条决策一个 Markdown 文件，README.md 做列表，跟代码一起评审和留历史。
   - Notion、飞书等文档工具：建一个数据库做列表，每条决策是其中一页。适合不看代码的人也要查。
   - 其他位置：告诉我路径或链接。
   ```

3. **用户选了仓库**：每条写成 `docs/decisions/D-NNN-<短标题>.md`，开头放第 4 节的字段表，正文按第 5 节；`docs/decisions/README.md` 维护列表，列出编号、决策、状态、日期。
4. **用户选了文档工具**：列表建成数据库，字段按第 4 节；每条决策是数据库里的一页，属性填字段，页面正文按第 5 节。工具不可用时，告诉用户卡在哪，不要换个地方偷偷写。

用户还没回答位置时，可以先在对话里把记录的内容给出来，确认位置后再落盘。

## 9. 完成后回复

记完后简短回复，不要把记录全文贴回对话：

- 记成了哪一条、状态、一句话结论，附链接或路径。
- 有取代关系时，说明旧记录改成了什么状态。
- 还在「待决定」的，列出来，说明在等什么。
- 下一步要做什么。

## 10. 完成标准

- [ ] 请示过的每一条都有真实分歧；显而易见的没有拿去问；每条写的是建议做法，不是是非题。
- [ ] 记录位置是用户定的，或沿用了项目已有的决策列表。
- [ ] 标题是结论；一条记录只有一个背景和目的。
- [ ] 背景让没参加讨论的人能看懂问题；目的写成可观察的结果。
- [ ] 做法具体到能照着实现；放弃的备选和原因写了。
- [ ] 代价写了；暂定的数字标明了由什么验证。
- [ ] 状态、决策人、关联都填了；有取代关系时，新旧两边都写了。
- [ ] 结论字段和正文一致。
