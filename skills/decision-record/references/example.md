## 正文

````markdown
## 背景：评论是怎么发到 PR 上的

服务不碰 GitHub，发评论的是用户仓库里的 CI（架构 §12.3）。每次推送都会走一遍下面的流程：

```mermaid
flowchart LR
  P[作者推送新提交] --> R[CI 的 review job<br/>提交审查、等结果]
  R --> S[服务审查<br/>返回报告]
  S --> C[CI 的 post job<br/>发总结评论 + 行间评论<br/>决定这个 job 红还是绿]
```

下面三条都是为了解决这个流程里会出现的问题。做法参考了 PR-Agent（①）和 Claude Code Review（②③）公开的做法。

## ① 不重复发同一条行间评论

- **会出什么问题**：作者每推一次，就重新审一次。上一轮已经报过、作者还没改的问题，这一轮又会被报出来。不处理的话，同一行上每推一次就多一条一模一样的评论。
- **目的**：一个问题在整个 PR 里只有一条行间评论。
- **做法**：每条行间评论的正文里带一个读者看不见的标记（HTML 注释），内容是这条发现的指纹（文件 + 去掉空白的代码片段，代码上下移动也不变）。CI 发之前先读一遍 PR 上已有的评论，有同样标记的就不再发。
- **为什么这样做**：另一种做法是服务在数据库里记「哪条发现发成了哪条评论」。但评论是 CI 发的，服务不知道评论编号，还要 CI 再回传；放在评论里的标记 CI 自己就能查，少一张表、少一个接口。
- **代价**：有人手动删了那条评论，下一轮会再发一次。

## ② 分清「没有问题」和「没有结论」

- **会出什么问题**：审查可能失败、超时，或者被新推送取代。如果 CI 只是「数一下有几个 🔴」，这些情况里数到的都是 0，job 显示绿色。作者和评审人会以为「审过了、没问题」，其实是「没审完」。打开合入门禁时更危险：审查挂了，门禁却放行。
- **目的**：只有审查真的做完了，CI 才把「没有 🔴」当成可以放行。
- **做法**：总结评论最后带一行 HTML 注释，读者看不见、程序能读：各级数量和是否完整，例如 `<!-- review-agents:counts {"blocking": 0, "important": 2, "robustness": 1, "nit": 3, "complete": false} -->`。整次审查失败或被取代时不写这一行。
- **「完整」怎么算**：所有维度都交了卷，并且所有报为 🔴 / 🟡 的发现都有结论。某个维度没交，或某条报为 🔴 / 🟡 的没验成，就是不完整，因为那里可能藏着 🔴。报为 🔵 的没验成只在报告里列出，不算不完整。
- **CI 怎么处理**：

| 结果 | CI 显示 | 合入门禁（开启时） |
| --- | --- | --- |
| 有验证成立的 🔴 | 失败 | 拦住 |
| 没有 🔴，审查完整 | 通过 | 放行 |
| 没有 🔴，审查不完整 | 未完成（不显示绿色） | 不放行 |
| 没有这一行（整次失败、被取代） | 未完成 | 不放行 |

- **代价**：模型服务一时不可用时，CI 会是黄的或红的，需要重跑。这是有意的：宁可让人知道「没审完」，也不要假装「没问题」。

## ③ 发不成行间评论的发现，放进总结

- **会出什么问题**：GitHub 只允许把行间评论发在这次 PR 改动到的行附近。但发现可能在没改的代码上：例如这次改了 `refund()`，问题却出在另一个文件里调用它的地方。这种评论会被 GitHub 拒收；不处理的话，这条发现就悄无声息地丢了。
- **目的**：验证过的发现一条都不丢。
- **做法**：服务生成报告时就按 diff 判断哪些发现能发成行间评论。不能的，在报告（总结评论）里单独一节「不在本次改动行上的发现」，节首一句说明原因，每条带级别、文件和行号、证据和建议。CI 发行间评论时被 GitHub 拒收的，也补进这一节。
- **代价**：这些发现不在代码旁边显示，作者要在总结里看。
````

## 这条样板做对了什么

- **标题就是结论。** 只看列表就知道定了哪三件事。
- **背景先讲流程。** 一张图说明评论是谁、在哪一步发的，没参加讨论的人也能看懂后面三个问题从哪来。
- **每项都从「会出什么问题」讲起**，并且带一个具体场景（推第二次、审查超时、问题在调用方）。
- **做法可以照着实现。** 标记的内容、注释的格式、CI 的四种结果都写死了。
- **为什么这样做写了被放弃的备选**（服务端记映射表）和放弃的原因。
- **代价写的是真实的副作用**，并说明为什么接受（宁可让人知道「没审完」）。
- **拆分留痕。** 结论和关联都写明它从 D-030 的第 5、7、8 项拆出。
- **只有一项的决策**，把「会出什么问题」并进背景，其余按 目的 → 做法 → 为什么这样做 → 代价与后续 写即可。
