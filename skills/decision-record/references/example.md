| 结论 | 从 D-030 第 5、7、8 项拆出：① 每条行间评论带隐藏标记，CI 发之前先查有没有同样的标记；② 总结评论末尾带一行隐藏的各级数量和「是否完整」，无 🔴 且完整才算通过；③ 不能发成行间评论的发现，在总结里单独一节列出并说明原因 |

**正文**

````markdown
## 背景：评论是怎么发到 PR 上的

服务不碰 GitHub，发评论的是用户仓库里的 CI。每次推送都会走一遍下面的流程：

```mermaid
flowchart LR
  P[作者推送新提交] --> R[CI 提交审查、等结果]
  R --> S[服务审查，返回报告]
  S --> C[CI 发总结评论和行间评论<br/>决定这个 job 红还是绿]
```

下面三条都是为了解决这个流程里会出现的问题。

## ① 不重复发同一条行间评论

- **会出什么问题：** 作者每推一次就重新审一次。上一轮报过、作者还没改的问题，这一轮又会报出来，同一行上每推一次就多一条一样的评论。
- **目的：** 一个问题在整个 PR 里只有一条行间评论。
- **做法：** 每条行间评论带一个读者看不见的 HTML 注释，内容是这条发现的指纹（文件 + 去掉空白的代码片段）。CI 发之前先读 PR 上已有的评论，有同样标记的不再发。
- **为什么这样做：** 另一种做法是服务在数据库里记「哪条发现发成了哪条评论」。但评论是 CI 发的，服务拿不到评论编号；标记放在评论里，CI 自己就能查，少一张表、少一个接口。
- **代价：** 有人手动删了评论，下一轮会再发一次。

## ② 分清「没有问题」和「没有结论」

- **会出什么问题：** 审查失败、超时或被新推送取代时，CI 数到的 🔴 都是 0，job 显示绿色。大家会以为「审过了、没问题」，其实是「没审完」。
- **目的：** 只有审查真的做完了，CI 才把「没有 🔴」当成可以放行。
- **做法：** 总结评论末尾带一行隐藏的各级数量和是否完整。

  | 结果 | CI 显示 | 合入门禁 |
  | --- | --- | --- |
  | 有验证成立的 🔴 | 失败 | 拦住 |
  | 没有 🔴，审查完整 | 通过 | 放行 |
  | 没有 🔴，审查不完整 | 未完成 | 不放行 |
  | 没有这一行 | 未完成 | 不放行 |

- **代价：** 模型服务一时不可用时，CI 不是绿的，需要重跑。这是有意的：宁可让人知道「没审完」。
````

## 2. 请用户拍板

**不好：** 背景和问题混在一大段里，每条都要读完才知道在问什么；还问了答案显而易见的事。

```text
关于行间评论挂在哪几行，发现常常跨好几行，其中只有一部分是这次 PR 改的，
一种做法是挂在重叠的那几行，GitHub 接受，作者也能看到上下文；另一种是……
你看哪种比较好？另外 D-030 那几项要不要也一起定一下？
```

**好：** 每条一行，括号里是建议；引用旧决策时写清第几项；显而易见的直接做，不拿去问。

```text
要你定的，每条一行，括号里是我的建议：
1. 说明审查员和维度审查员同时跑、同一优先级、最晚第 20 分钟交卷？（是）
2. 改动说明不另派人验证，只由程序核对引用的文件和行号？（是）
3. 先做依据（#68），再做报告（#11），最后做改动说明（#67）？（是）
4. nit 合并那一次模型调用最多等 2 分钟？（是）

另外，D-030 第 5 项（行间评论用隐藏标记去重）沿用，不需要再定。
```
