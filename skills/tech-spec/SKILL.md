# 技术规格文档

技术规格实现产品规格里的业务合同，不另立产品范围。先读已有产品规格，再把验收、规则与边界落到架构、契约与决策。没有业务合同就写接口，会把实现上的方便写成产品范围。业务目标、故事与验收的改口属于产品决策，回到 product-spec 的决策日志，不要在这里改业务。实现约束若迫使用户可见结果变化，停止并说明冲突，请用户先改产品规格。

## 前置

1. 找到本案产品规格（对话、仓库或用户给出的路径）。Read 全文。
2. 没有文档，或文档中没有可引用的验收与业务规则时，停止。不要起草接口、架构或测试决策来填空。
3. 读到的验收、规则与边界是合同。技术规格逐条覆盖这些合同，不新增产品能力，不删掉已承诺的结果。
4. 旧稿若夹杂接口与实现，只把其中的业务目标、规则、边界与验收当作合同。与业务合同冲突的旧契约在技术决策日志中改写，不要把旧接口当成不可改的产品决定。

没有产品规格时，ALWAYS 只输出：

```markdown
# 尚无产品规格

请先用 product-spec 写清业务目标、业务结构、用户故事、功能规则、边界与验收。技术规格只实现已有业务合同，不在这里补产品范围。
```

有文档但缺验收或业务规则时，在这段之后加一行：`缺口：缺少验收` 或 `缺口：缺少业务规则`。

## 何时读取参考

产品规格已可读之后，落笔前 Read `skills/tech-spec/references/sections.md` 的对应段。未读不要落笔。用户要完整技术规格，或要对照契约表、架构图与决策如何合成一篇时，再 Read `skills/tech-spec/references/example.md`。只改一段且该段指导已够时，不读示例全文。示例中的商家导出假定产品规格已存在，只作写法对照。

## 对内核对（默认不展示）

核对过程不写入回复。仅当用户要求「展开评审过程」时，才简要说明对照了哪些段。

- 已读产品规格全文。每一条验收在第 1 节有一行，并在契约或检查项中有落点。
- 没有产品规格未写的能力被写成既定范围。
- 复杂时业务架构图与技术架构图都在。不复杂时两节都写了「本期不附图」及一句边界。复杂的判定见 `references/sections.md`。
- 同一事实只在一张表里展开，他处指向该表。
- 未决含已掌握事实、待决问题、禁止实现的假设、责任人与期限。

## 对外输出

ALWAYS use this exact structure. 评审已有技术文档时也按这些标题组织：已写的保留，缺失的在该段写明缺口。不要编造产品规格里没有的能力，也不要在文末另附检查清单。

## 落盘

产出完整技术规格时，写入仓库的 `docs/`。目录不存在就创建。默认文件名：`docs/<短标题或slug>-技术规格.md`。短标题与产品规格同一事项对齐，简短可读。用户指定了路径或文件名时，用该路径。不要覆盖产品规格文件。

对话以一行开始：`已写入 docs/<文件名>`。文件是交付物。调用方仍要在对话里看到模板时，这一行之后附上已写入的同一正文，不要另写一版。

没有可写仓库时，不要假装已经落盘。在对话中按上面的模板输出全文，并加一行：当前没有可写仓库，规格只在对话中给出。

「尚无产品规格」不是完整技术规格，只在对话中输出，不写入 `docs/`。

## Example

**Input：** 「产品规格已经有了『商家批量导出订单』。接口怎么定，验收怎么实现？」

**Output：** 先 Read 该产品规格。没有可引用的验收与业务规则则停止，并只输出「尚无产品规格」。有则 Read `skills/tech-spec/references/sections.md`，再 Read `skills/tech-spec/references/example.md`，按该示例的详略另起一篇。不新增产品能力。成稿写入 `docs/`，例如 `docs/商家批量导出订单-技术规格.md`。
